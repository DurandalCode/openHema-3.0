# Пакет согласования замечаний — 2026-09-25

**Статус: независимая первая волна реализована локально; условные треки ждут решений.** База аудита —
`3506b03`. [Отчёт интеграции](integration-report.md) отделяет сделанный код от
открытой живой приёмки. Пакет можно согласовать частями: открытый вопрос по тарифам не блокирует арену.

Инструкции проведённого запуска: [четыре реализации + QA + памятка](launch-now.md). Основной чат только координировал.

## Как читать и согласовать

1. [Решения](decisions.md): что уже решил пользователь и что только предложено.
2. [Волны и владение файлами](waves.md): что запускать вместе и что после мержа.
3. [Небольшие правки и проверка существующего](small-fixes.md).
4. Нужные spec → plan → tasks из таблицы ниже.
5. [Инструкции для отдельных чатов](handoff.md): готовые стартовые сообщения.

Формат согласования: перечислить принятые D-ID и поправки к остальным, например
«D-API, D-BULK и D-EXPORT принимаю; в D-0054-1 нужен публичный экран».
Координатор переносит **фактический ответ** в decisions, устраняет расхождения
spec/plan/tasks и ставит ready только выбранным трекам. Пустая клетка или
прошедшее время не считаются одобрением. До этого рабочим чатам можно поручать
ревью документов, но не реализацию условных правил.

## Условия передачи в реализацию

- Принятые решения перенесены в документы; выбранные spec/plan готовы.
- Пакет закоммичен в общую базу; у каждого чата своя ветка и worktree от
  указанного **фактического commit**, включающего зависимости.
- Общие файлы имеют одного владельца на волну. Мерж и интеграционная приёмка
  последовательные; запуск следующей волны не происходит просто по окончании таймера.
- Рабочий чат сдаёт изменения и свидетельства проверок, не ставит весь
  backlog в done. Непроверенные ручные AC остаются открытыми.

Оценки в днях не даны: без измерения времени первого трека они были бы
выдуманным обещанием. Расписание задано зависимостями и условиями выхода волн.
