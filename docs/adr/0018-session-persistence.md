# ADR 0018: Персистентность refresh-сессий

- Статус: принято
- Дата: 2026-08-29

## Контекст

Аутентификация сегодня (спеки 0007, 0037) полностью stateless: access и
refresh — подписанные JWT, сервер не хранит ни одной строки о том, какие
сессии выданы. `0037` (решение 6) уже упёрлась в предел этой модели: смена
пароля должна была бы обрывать все сессии пользователя, но обрывает только
**продление** — отзывает возможность получить новую пару токенов по
`Refresh`, а уже выданный короткоживущий access долетает до конца своего
TTL сам. Блок «Безопасность» кабинета (макет 19a, `0038`) по этой же
причине не нарисован — список сессий нечего показывать, потому что их
негде хранить (`0038`, FR-26).

`docs/adr/0017-deferred-debt-porting-order.md` (п. 4.2) прямо называет
разворот этого решения «своей ADR внутри `0042`» и предупреждает, что это
не сюрприз, а плановая часть работы. Спека `0042-account-mail-and-files`
(FR-10..FR-17) формулирует требования; эта ADR фиксирует архитектурное
решение, которое эти требования реализует.

## Решение

### 1. Реестр — только refresh, не access

Access-токен остаётся полностью stateless: как и сегодня, его валидность
проверяется исключительно подписью и `exp`, без обращения к БД на каждый
запрос. Это осознанно сохраняемое свойство, не компромисс — access живёт
15 минут (`JWT_ACCESS_TTL`), и добавление проверки реестра на каждый запрос
меняло бы профиль производительности системы ради выигрыша в 15 минут
худшего случая.

Персистентность заводится только для refresh: каждая выдача сессии (вход,
регистрация) создаёт строку в новой таблице `auth.sessions`:

```sql
CREATE TABLE auth.sessions (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    expires_at   TIMESTAMPTZ NOT NULL,
    revoked_at   TIMESTAMPTZ NULL
);
```

Refresh-токен несёт новый клейм `sid` — id строки реестра. `Refresh`
проверяет: сессия существует, `revoked_at IS NULL`, не просрочена — и
только затем выпускает новую пару токенов, обновляя `last_seen_at`.
Access-токен клейма `sid` не несёт.

### 2. Что отзывается мгновенно, что доживает свой TTL

Отзыв сессии (поштучный, «выйти со всех устройств», смена/сброс пароля)
ставит `revoked_at` немедленно. Эффект:

- **Продление отзывается мгновенно.** Следующий `Refresh` по этой сессии
  отклоняется, даже если refresh-токен ещё не истёк по `exp`.
- **Уже выданный access долетает до конца своего TTL.** Он не привязан к
  `sid` и не отозван — отозвана только строка сессии, из которой этот
  access когда-то был выпущен. Отозванный доступ живёт максимум 15 минут
  после отзыва.

Это ровно та же граница, что `0037` (решение 6) уже приняла для смены
пароля, — эта ADR формализует её и распространяет на все причины отзыва
(поштучный отзыв, «выйти со всех устройств», сброс пароля). Мгновенный
отзыв access потребовал бы проверки реестра на каждый запрос — отклонено
по той же причине, что и в п. 1.

### 3. Реестр не хранит устройство, браузер или IP

Решение пользователя (2026-08-28, спека `0042`, решение 2): строка сессии
несёт только `id`, `created_at`, `last_seen_at`. Список в кабинете
различает сессии по времени создания и последней активности, отмечает
текущую — и всё. IP и `User-Agent` не пишутся ни при создании, ни при
`Refresh`.

Альтернатива — полноценный реестр устройств («Chrome, Москва, 91.x.x.x»),
как в блоке «Безопасность» макета 19a буквально, — отклонена: это новые
персональные данные (геолокация по IP, отпечаток браузера) ради косметики
экрана, не подкреплённые доменной потребностью текущей спеки. Если
понадобится позже — это отдельное решение с отдельной оценкой приватности,
не молчаливое расширение этой таблицы.

### 4. Судьба уже выданных токенов без `sid`

Refresh-токены, выпущенные до выката этой фичи, не несут клейма `sid`.
`Refresh` трактует его отсутствие как невалидный токен (`ErrInvalidCredentials`)
— пользователь просто входит заново, ровно как если бы refresh истёк
естественным образом.

Альтернатива — «grandfather для токенов без `sid`» (пропускать проверку
реестра, если клейма нет) — отклонена: она оставляла бы постоянную дыру в
отзыве (токен без `sid` никогда не попадает под `RevokeUserSessions`) на
неопределённый срок вместо разового неудобства в момент выката.

### 5. Очистка реестра

`Repository.DeleteExpiredSessions` вызывается фоново (при старте
приложения и периодически) и физически удаляет строки с истёкшим
`expires_at`, отозванные или нет. Реестр не растёт бесконечно вместе с
логами входов — он не журнал, а таблица текущих и недавно истёкших сессий.

## Область действия

Решение касается только модуля `auth` и клейма `sid` в `pkg/jwt`. Другие
модули по-прежнему не обращаются к таблице `auth.sessions` напрямую — им
она не нужна: межмодульная точка входа для «получателя уведомления»
(`auth.Recipients`, спека `0042`) читает `auth.users`, не сессии.

## Последствия

- `pkg/jwt.Manager.Issue` получает третий параметр `sessionID string`;
  `Claims.SessionID` кладётся только в refresh.
- `Login`/`Register` создают строку `auth.sessions` перед выпуском токенов.
  `Refresh` читает `sid`, проверяет активность, обновляет `last_seen_at`.
- `ChangePassword` отзывает все сессии пользователя, кроме текущей;
  `ResetPassword` — все без исключения (сброс не выдаёт сессию сам, спека
  0037 решение 5 — отзывать «текущую» ему нечего).
- `Logout` отзывает текущую сессию на сервере, а не только стирает cookie
  в браузере.
- Один прямой выигрыш сверх требований спеки: если когда-нибудь
  понадобится глобальный kill-switch («заблокировать пользователя
  немедленно»), таблица сессий даёт для него готовую точку — при условии,
  что мгновенность всё ещё будет означать «в пределах TTL access», как
  зафиксировано в п. 2.

## Альтернативы

- **Полный отказ от JWT в пользу opaque-токенов, проверяемых по БД на
  каждый запрос** — отклонено: это меняет профиль производительности всей
  системы (БД на каждый запрос вместо только на `Refresh`, раз в 15 минут)
  ради свойства, которого требования не просят (мгновенный отзыв доступа).
- **Только access, без реестра refresh** («смена пароля перевыпускает
  секрет подписи») — отклонено ещё на этапе `0037`: перевыпуск общего
  секрета обрывает сессии **всех** пользователей разом, а не одного.
- **Реестр с полным профилем устройства** (см. п. 3) — отклонён решением
  пользователя как избыточные персональные данные без доменной
  потребности.
