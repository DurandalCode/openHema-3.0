# ADR 0015: Портирование редизайна OpenHEMA — порядок и границы

- Статус: принято
- Дата: 2026-08-12

## Контекст

В `claude.ai/design` есть проект «OpenHEMA» (id `f5a761fd-ed71-4a5b-92f9-5690246f70af`,
тип `PROJECT_TYPE_PROJECT`, **не** design-system — read-only источник через
`DesignSync(get_file)`/`DesignSync(list_files)`, ничего туда не пишем и не
пушим). Дизайн-агент провёл там полный визуальный редизайн большей части UI
`web/src`: единая палитра/типографика/радиусы/высоты, 14 переиспользуемых
примитивов (`Ui*.dc.html`), и ~20 экранов админки и публичной части, каждый
в обеих темах.

Файлы — формат `*.dc.html` (`<x-dc>`-шаблон + `class Component extends
DCLogic { renderVals() }`), не React/TSX. Перенос в `web/src` — не копирование,
а переписывание каждого файла в TSX-компонент по конвенциям `web/AGENTS.md`
(FSD-слои, Tailwind v4, `next-themes`).

Объём эквивалентен редизайну всего UI-слоя: единой спекой не описать (ADR
0008 — «крупное решение → отдельный ADR», спека — на одну фичу). Эта ADR
фиксирует **сквозное решение о порядке и границах**, каждый пункт порядка —
последующая отдельная `docs/specs/NNN-*/`.

### Разведка

Проведена полная читка всех `.dc.html` (включая `github.md` — манифест,
оставленный самим дизайн-агентом внутри проекта, и `drafts/*`) и сверка
каждого экрана/компонента с реальным состоянием репозитория на момент
2026-08-12 (proto, `web/src/entities|features|widgets|app`, `globals.css`,
`shared/ui`).

**`github.md` не является источником истины** — он описывает сам себя как
манифест дизайн-агента, и разведка нашла в нём конкретные неточности:

1. Файл `Публичная главная.dc.html` из его screen map на деле называется
   `Публичная главная v2.dc.html` (реальный список файлов проекта это
   подтверждает; `v1` — в `drafts/`, архив).
2. `Номинации.dc.html` (список номинаций турнира, спека 0003, экран
   `app/(admin)/admin/nominations/page.tsx`) — легитимный отдельный экран,
   полностью отсутствующий в screen map github.md.
3. «Турнир и форматы.dc.html» описан как «два **недостающих** раздела
   админки» — неверно: `tournament`/`formats` роуты, фичи
   `tournament-settings`/`format-presets`, proto `Contact`/`FormatPreset`/
   `ListFormatPresets` и т.д. полностью реализованы (спеки 0001, 0020, обе
   done). Это чистый визуальный редизайн, не новая фича.
4. Карта репозитория в `Дизайн-система.dc.html` называет целевые пути
   `shared/ui/Button/Button.tsx` (папка-на-компонент) и
   `features/fighter/FighterCard.tsx` — ни то, ни другое не соответствует
   реальной структуре (`web/src/shared/ui/*.tsx` плоские файлы;
   актуальный fighter-срез — `features/fighter-management/`).
5. `Drafts.dc.html` объясняет архивацию `Tournament Console.dc.html` как
   «заменён экраном «Турнир и форматы»» — неверно: по содержанию это разные
   функции (живой операционный дашборд оператора турнира — очередь боёв,
   прогноз по номинации, лента «требует внимания» — vs профиль турнира и
   библиотека пресетов формата).
6. `Схема номинации.dc.html` ссылается на `Playoff Bracket.dc.html` как на
   существующий внешний экран для сетки, но этот файл лежит в `drafts/` и
   сам `Drafts.dc.html` помечает его архивным («логика переехала в «Схему
   номинации»»). Репозиторий подтверждает архивную версию верной: сетка
   уже встроена прямо в `stages/[stageId]/page.tsx` (`BracketSeeding`), а не
   отдельный экран.

Полные отчёты разведки (токены/компоненты/тема — фундамент; экраны/drafts/
расхождения — по каждому файлу) использованы при написании этой ADR и
`docs/specs/0022-design-system-foundation/spec.md`; в код не включены (см.
`plan.md` соответствующих спек за деталями по мере продвижения). Сверенная
карта «экран/компонент → repo-путь» вынесена в `docs/design-sync.md` —
она, а не `github.md` дизайн-проекта, источник истины для последующих спек
и для будущих редизайнов (там же — как проводить разведку в следующий раз).

## Решение

### 1. Порядок инкрементов

Каждый пункт — отдельная `docs/specs/NNN-<kebab-feature>/`. И номер `NNN`, и
имя `kebab-feature` **фиксируются здесь заранее** (по явному решению
пользователя, вопреки обычной практике этого репозитория — числа обычно
присваиваются на момент старта спеки, см. `docs/specs/README.md`). Порядок
обоснован зависимостями (примитивы раньше экранов) и сложностью (простые
табличные экраны — «разогрев» паттернов перед самыми сложными DnD-экранами):

1. `0022-design-system-foundation` — **Фундамент: токены + примитивы** (уже
   создана) — `tokens.css`/интеграция в `next-themes`, 12 shared/ui-примитивов
   (без `UiFighterCard`, без `UiSideNav` как отдельного публичного компонента
   — см. «Границы» ниже), единый `AppShell` вместо `AdminShell`/`AdminShellLight`.
2. `0023-shared-feedback-patterns` — **Общие паттерны обратной связи** — то,
   что не попало в список 14 примитивов, но нужно почти всем следующим
   экранам: `datetime-field`, `tooltip`, `pagination`, `breadcrumbs`,
   toast-семейство (новая зависимость — конкретный выбор в `plan.md` своей
   спеки), правило toast/inline-error/модалка из «Состояния и обратная
   связь.dc.html». Доменные паттерны (потеря связи на арене — локальная
   очередь очков, автореконнект) — не сюда, идут в `0033-arena-live-ui-redesign`
   (п.12, там же домен).
3. `0024-users-redesign` — **Пользователи** — таблица + фильтры + модалка
   создания админа, минимум кастомной логики поверх примитивов.
4. `0025-applications-redesign` — **Заявки** — воронка по статусам, история
   событий заявки.
5. `0026-fighters-redesign` — **Бойцы** — ростер + карточка бойца; включает
   `UiFighterCard` (это фича-уровневый компонент `features/fighter-management/`,
   не общий примитив — см. п.6 разведки, — поэтому не в
   `0022-design-system-foundation`).
6. `0027-arenas-redesign` — **Арены** — список площадок с живым статусом,
   reorder, архив/восстановление.
7. `0028-nominations-list-redesign` — **Номинации** — список номинаций
   турнира (спека 0003), пропущен в screen map github.md, но легитимен.
8. `0029-tournament-and-formats-redesign` — **Турнир и форматы** —
   визуальный редизайн (форма + live-превью, библиотека пресетов), API уже
   полностью существует.
9. `0030-nomination-pools-redesign` — **Посев — группы** — ограниченный DnD
   (пулы + нераспределённые), шаг перед самым сложным экраном.
10. `0031-nomination-schema-redesign` — **Схема номинации** — конструктор
    схемы: DnD-граф этапов, инспектор, диагностика схемы. Один из двух самых
    сложных пунктов — после разогрева на `0030-nomination-pools-redesign`.
11. `0032-stage-page-redesign` — **Страница этапа** — превью формирования с
    дележами/пересечениями, undo/сброс этапа; сразу за
    `0031-nomination-schema-redesign` (общий домен, соседние экраны).
12. `0033-arena-live-ui-redesign` — **Табло арены + Панель секретаря +
    Страница арены** — один UI-паттерн в трёх файлах дизайна (переключение
    режимов «Управление ареной» / «Ведение боя» на одной странице/URL) —
    архитектурное решение о переключателе принимается внутри этой спеки,
    делать одним блоком; сюда же доменные паттерны потери связи из п.2.
13. `0034-public-home-redesign` — **Публичная главная v2** — после админки,
    переиспользует устоявшиеся решения по примитивам.
14. `0035-public-nomination-redesign` — **Публичная — номинация**.
15. `0036-public-applications-redesign` — **Публичная — заявки**.
16. `0037-auth-profile-api-extension` — **мини-цикл на новый API** для
    «Вход, кабинет, о платформе»: сброс пароля (RPC + email), новые поля
    `Tournament` («главный судья», регламент-PDF). Предшествует п.17;
    остаётся ли это отдельной спекой или разделом `plan.md` самого экрана —
    решается при подходе очереди (см. «Решения по открытым вопросам», п.4) —
    номер и имя зарезервированы на случай отдельной спеки.
17. `0038-auth-profile-redesign` — **Вход, кабинет, о платформе** — UI
    поверх API из п.16; последний инкремент этой ADR.

`drafts/*` — не переносятся (см. «Границы»).

### 2. Границы (решено разведкой, без открытых вопросов)

- **`UiSideNav`** — в галерее дизайн-системы показан только как
  «альтернатива верхней навигации», реальными экранами не используется.
  Не портируется как отдельный публичный `shared/ui`-компонент в фундаменте;
  топ-навигация (соответствует реальному `admin-nav.tsx`) остаётся
  единственным паттерном.
- **`AdminShell`/`AdminShellLight`** схлопываются в один `AppShell`,
  тема которого переключается тем же `next-themes`-механизмом, что и весь
  остальной UI (без раздельных компонентов на тему).
- Список пунктов навигации в `AppShell` строится по **реальным роутам**
  (`admin-nav.tsx`: Пользователи/Турнир/Номинации/Форматы/Площадки/Заявки/
  Бойцы/+Создать админа), а не по хардкод-дефолту дизайна (там лишний
  несуществующий пункт «Пульт» — наследие архивного Tournament Console,
  и подпись «Арены» вместо реальной «Площадки»).
- **Механизм темы**: дизайн передаёт `theme="dark"|"light"` явным пропом
  в каждый компонент (JS lookup по таблице хексов, инлайн `style`) — прямое
  противоречие ADR 0005 (`next-themes`, `.dark`-класс, CSS-переменные).
  Решение: портирование = редизайн каждого примитива под существующий
  механизм (`bg-background`/CSS-переменные), проп `theme` **не переносится**.
  Это не развилка — единственный вариант, совместимый с ADR 0005.
- **`UiField`** в моках нефункционален (нет реального `onChange`, `value` —
  статичный текст). Портируется как настоящий контролируемый компонент
  поверх существующих `input.tsx`/`label.tsx`/`select.tsx`, а не буквальная
  транскрипция разметки.
- **`UiModal`** рестайлится поверх существующего `dialog.tsx` (Radix —
  focus-trap/ESC/ARIA уже есть), не переписывается с нуля как
  позиционированный `div`, как в моке.
- Раздел «8 добавок» в «Состояния и обратная связь.dc.html» неточен: 3 из 8
  (`select`, `dropdown-menu`, `avatar`) и `skeleton` уже есть в `shared/ui` —
  реально новых компонентов 5 (см. п.2 порядка).

## Решения по открытым вопросам

Заданы пользователю через `AskUserQuestion` 2026-08-12, ответы закрывают все
пункты — открытых вопросов для запуска спеки 0022 не осталось:

1. **Ребрендинг палитры — полный.** Новая hex-палитра дизайна (красный
   акцент) принимается целиком; существующие shadcn/oklch-переменные
   (`--primary`, `--accent`, `--gold`, ...) перекрашиваются под неё — один
   источник токенов, без параллельного набора. Брендинг спеки 0004
   (зелёный+золото) заменяется этим инкрементом.
2. **Стратегия примитивов — рестайлинг на месте.** Компоненты с прямым
   текущим аналогом (`button.tsx`, `badge.tsx`, `tabs.tsx`, `card.tsx`,
   `dialog.tsx` и т.д.) получают новые варианты/токены в тех же файлах, без
   параллельного набора `Ui*`-компонентов. Примитивы без прямого аналога
   (тег, чип фильтра, заголовок/строка таблицы) добавляются как новые файлы
   в том же `shared/ui`.
3. **`drafts/Tournament Console.dc.html` — не рассматривается.** Полностью
   вне скоупа этой инициативы редизайна, без резервирования места в порядке.
   Если понадобится в будущем — отдельная фича с нуля (новый API), не
   связанная с этой ADR.
4. **«Вход, кабинет, о платформе.dc.html» — включается с под-циклом на API.**
   Остаётся последним инкрементом порядка (`0038-auth-profile-redesign`,
   п.17), но с явной оговоркой:
   новые backend-потребности (сброс пароля + email, поля `Tournament`
   «главный судья»/регламент-PDF) идут отдельным мини-циклом **до**
   `spec.md`/`plan.md` самого экрана, а не встраиваются в UI-спеку молча.

## Обоснование

- Разбиение по инкрементам — прямое следствие ADR 0008 (спека = одна фича,
  не весь UI-слой) и объёма (эквивалент редизайна всего клиента).
- Порядок «примитивы → простые табличные экраны → сложные DnD-экраны →
  публичные → экран с новым API» минимизирует риск: сначала стабилизируются
  переиспользуемые паттерны на дешёвых экранах, затем идут дорогие.
- Явная сверка с репозиторием (не слепое доверие `github.md`) — единственный
  способ не унести в спеки вымышленный скоуп (пример — «Турнир и форматы»
  описан дизайн-агентом как новая фича, а на деле чистый визуал).

## Последствия

- Номера `0022`–`0038` зарезервированы за этим порядком целиком (список
  выше) — отступление от обычной практики репозитория (числа обычно
  присваиваются на момент старта спеки, см. `docs/specs/README.md`),
  принятое сознательно по решению пользователя. **Риск**: если между
  стартами этой инициативы понадобится несвязанная спека, её номер будет
  вынужден пропустить зарезервированный диапазон (взять следующий за 0038)
  либо, если диапазон уже начал использоваться не по порядку, придётся
  перенумеровать оставшиеся зарезервированные пункты и обновить эту ADR и
  `docs/specs/README.md` синхронно — сам список (порядок и имена) при этом
  не меняется, только числа.
- `docs/specs/README.md` держит зарезервированные номера как строки со
  статусом «резерв», ссылающиеся на эту ADR, — чтобы `write-spec` не выдал
  тот же номер случайно несвязанной фиче.
- `drafts/*` (все файлы, включая `Tournament Console`) в скоуп редизайна не
  входят и не резервируются.
- Спека 0004 (палитра зелёный+золото) считается **заменённой** результатом
  спеки 0022 в части цветовых токенов — её решение о палитре больше не
  действует, остальное (навигация без скрытых переходов и т.д.) не
  затрагивается.
- Инкремент «Вход, кабинет, о платформе» не может стартовать с одного
  `spec.md` — потребует явного мини-цикла на новый API до UI-части; это
  фиксируется здесь заранее, чтобы при подходе очереди не забылось.

## Альтернативы

- **Один инкремент на весь редизайн** — отклонено: ADR 0008 требует
  разбиения нетривиальной фичи, риск неуправляемого PR на весь UI-слой.
- **Порядок «по алфавиту»/как встретилось в списке файлов** — отклонено:
  не даёт «разогрева» паттернов перед сложными экранами, не использует
  зависимость примитивы→экраны явно.
- **Доверять `github.md` как финальной правде и не сверять с репозиторием**
  — отклонено: разведка уже нашла 6 конкретных неточностей (см. «Контекст»),
  включая ложное «недостающие разделы» для полностью готовой фичи.
