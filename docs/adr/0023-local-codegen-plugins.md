# ADR 0023: Кодген — локальные плагины в образе, а не удалённое исполнение

- Статус: принято
- Дата: 2026-09-17

## Контекст

Генерация кода из контрактов была настроена на **удалённое исполнение
плагинов**: все три генератора объявлялись в `proto/buf.gen.yaml` как
`remote: buf.build/...`, то есть работу выполнял не локальный `buf`, а внешний
реестр (BSR).

2026-09-17 при разворачивании препрода выяснилось, что с ВМ это не работает:

```
$ make generate
cd server && go tool buf generate ../proto --template ../proto/buf.gen.yaml
Failure: permission_denied: 403 Forbidden
```

Проверено на самой ВМ:

- `buf.build` отдаёт `403 Forbidden` на **любой** запрос, включая корневую
  страницу (`curl https://buf.build/`) — это блокировка по адресу, а не
  проблема авторизации или токена.
- Заблокирован только он: `proxy.golang.org` → 200, `registry.npmjs.org` →
  200, Docker Hub → 401 (достижим), GitHub → 200.
- Сам инструмент исправен: `buf lint` и `sqlc generate` на ВМ проходят — они в
  реестр не ходят.

Обойти было нечем: `make deploy` начинается с `make codegen`, gen-код в
репозитории не хранится (ADR 0004), а образы `server`/`web` собираются из
контекста хоста — значит результат генерации обязан физически существовать на
ВМ **до** `docker compose build`. Деплой был заблокирован целиком.

Дополнительно вскрылось, что зависимость от реестра ничего не давала взамен:
версии плагинов в `buf.gen.yaml` не фиксировались (брались «последние»), и к
этому моменту уже разъехались с runtime — код генерировался `protoc-gen-go
v1.36.12` при `google.golang.org/protobuf v1.36.11` в `go.mod` и
`protoc-gen-es v2.15.0` при `@bufbuild/protobuf 2.12.1` в lock-файле.

## Решение

**Плагины кодгена — только локальные (`local:`), а средой их исполнения служит
отдельный образ, а не хост-машина.**

1. `proto/buf.gen.yaml`: `remote:` → `local:` (`protoc-gen-go`,
   `protoc-gen-connect-go`, `protoc-gen-es` — по имени бинаря в `PATH`).
2. `deploy/codegen.Dockerfile`: стадия `golang:1.26-alpine` собирает `buf` и
   оба Go-плагина, финальная `node:22-alpine` несёт их и `protoc-gen-es`.
3. `make generate` запускает `buf` в контейнере поверх смонтированной рабочей
   копии (`-u $(id -u):$(id -g)` — чтобы сгенерированное принадлежало хозяину
   репозитория, а не root).
4. **Образ не хранит собственного списка версий.** `buf`, `protoc-gen-go`,
   `protoc-gen-connect-go` собираются из `server/go.mod`; `protoc-gen-es`
   ставится по версии из `web/package.json`. Обе пары «генератор = runtime»
   выровнены (`protobuf` → v1.36.12, `@bufbuild/*` → 2.15.0).
5. Два стража от регресса — в разных тестовых наборах, потому что path-фильтры
   CI разводят их по разным джобам:
   - `server/internal/codegen/buf_gen_config_test.go` — падает на любом
     вернувшемся `remote:`-плагине;
   - `web/codegen-versions.test.ts` — падает, если версия `protoc-gen-es`
     перестала быть точной или разошлась с `@bufbuild/protobuf`.
6. CI: генерация выполняется один раз в отдельной джобе `codegen`, результат
   едет остальным артефактом (было — семь независимых генераций).

## Обоснование

- **Снимает причину, а не симптом.** После перехода обращений к `buf.build` не
  остаётся вовсе (`buf.lock` пуст, BSR-зависимостей у модуля нет), поэтому
  доступность чужого сервиса перестаёт влиять на деплой.
- **На хост ничего не ставится.** Требование пользователя: препрод-ВМ не
  обрастает тулчейнами; Docker там и так есть. Кодгену больше не нужны на
  хосте ни Node, ни (для самого кодгена) Go.
- **Версии становятся воспроизводимыми.** Они и так обязаны быть в манифестах
  — теперь оттуда же берётся и генератор, поэтому «сгенерировано не тем»
  структурно невозможно, а не ловится глазами.
- **Проверяемость.** Результат перехода подтверждён побайтовым совпадением с
  эталоном, снятым до правок (29 файлов), и зелёным существующим корпусом
  тестов без единой правки прикладного кода.

## Последствия

- **Для кодгена нужен Docker.** Раньше хватало Go на хосте. Для проекта это не
  новое требование (стек и так поднимается через compose), но `make generate`
  теперь не работает там, где Docker не запущен.
- **Первая сборка образа платная** (компиляция `buf` — 74 МБ бинарь): ~27 с на
  ноутбуке, на 2-CPU ВМ дольше. Дальше — попадание в кеш слоёв, и `make
  generate` укладывается в ~1 с. Слой пересобирается только при смене версий в
  `server/go.mod`/`web/package.json`.
- **`sqlc`, `goose`, `buf lint` остаются хостовыми** (`go tool`) — они в
  заблокированный реестр не ходят, и трогать их не за чем. Перенос и их в
  контейнер возможен, но к этой проблеме отношения не имеет.
- **CI стал дешевле**: одна генерация вместо семи, web-джобы больше не ставят
  Go (он был нужен им только ради `buf`). Плата — остальные джобы ждут
  `codegen`.
- ADR 0004 (не хранить gen-код в репозитории) **остаётся в силе**: меняется
  способ генерации, а не место хранения.

## Ограничения окружения препрод-ВМ (выяснены при приёмке)

Оба найдены не в теории, а при первой же сборке образа на самой ВМ, и оба
влияют на то, как можно писать этот Dockerfile:

1. **BuildKit на ВМ недоступен.** Плагин `buildx` не установлен, а
   `DOCKER_BUILDKIT=1` падает с `BuildKit is enabled but the buildx component
   is missing or broken`. Docker там собирает классическим билдером, поэтому
   `deploy/codegen.Dockerfile` не должен содержать BuildKit-only синтаксиса —
   в частности `--mount=type=cache` (первая редакция его содержала и упала).
2. **У контейнеров на ВМ нет DNS-егресса.** Цепочка `DOCKER-USER` (см.
   `/etc/ufw/after.rules`, блок `UFW-DOCKER FIX (hema)`) устроена
   направленно-нейтрально:

   ```
   -A DOCKER-USER -m state --state RELATED,ESTABLISHED -j RETURN
   -A DOCKER-USER -p tcp -m tcp --dport 3000 -j RETURN
   -A DOCKER-USER -p tcp -m tcp --dport 80   -j RETURN
   -A DOCKER-USER -p tcp -m tcp --dport 443  -j RETURN
   -A DOCKER-USER -j DROP
   ```

   Наружу разрешён только TCP 80/443/3000, а **UDP 53 дропается** — поэтому
   контейнер не резолвит имена (`wget: bad address`), и сборка виснет на
   `go: downloading` без нагрузки на CPU. Хост при этом ходит в сеть нормально.
   Обход — собирать образ с `--network host` (сборочный контейнер не идёт через
   `FORWARD` и правила не касается); он и зашит в цель `codegen-image`.

   **Это дефект шире кодгена**: любой контейнер стека, которому нужен выход в
   интернет по имени, там работать не будет — в первую очередь отправка почты
   из `server` (SMTP, спека 0042). Аккуратное лечение — разрешить контейнерам
   егресс одним правилом перед `DROP` (например `-A DOCKER-USER -s
   172.16.0.0/12 -j RETURN`, либо узко `-p udp --dport 53 -j RETURN`), после
   чего `--network host` из сборки можно убрать. Решение за владельцем ВМ:
   правка firewall выходит за рамки этой спеки.

## Отклонённые варианты

- **Поставить Node/pnpm на хост ВМ и генерировать там.** Работает, но
  противоречит требованию «на ВМ ничего не доустанавливаем» и множит ручные
  зависимости хоста.
- **Генерировать на машине разработчика, доставлять результат на ВМ**
  (rsync/архив). ВМ перестаёт быть самодостаточной, появляется риск
  рассинхрона «контракты ↔ сгенерированный код», который нужно ловить
  отдельной проверкой.
- **VPN/прокси/зеркало реестра на ВМ.** Лечит симптом, оставляет зависимость
  от доступности чужого сервиса и добавляет сетевую магию в деплой.
- **Собирать образы в CI и выкатывать из registry** (ВМ только `docker compose
  pull`). Решает задачу шире и попутно снимает медленную сборку на 2 CPU, но
  это отдельная перестройка деплоя — не смешиваем с починкой кодгена.
- **Коммитить gen-код в git.** Прямой конфликт с ADR 0004.
- **Брать `buf` из официального образа `bufbuild/buf`** вместо сборки из
  `go.mod`. Быстрее собирается, но продублировало бы версию `buf` в
  Dockerfile — то самое, чего это решение избегает. Держим в уме как запасной
  вариант, если время сборки на ВМ окажется неприемлемым (тогда версию
  придётся сверять ещё одним стражем).
