# ADR 0019: Файловое хранилище — порт и локальный том

- Статус: принято
- Дата: 2026-08-29

## Контекст

Профиль турнира сегодня хранит два изображения-и-документа исключительно
внешними ссылками: эмблему (`0001`) и регламент (`0037`, решение 2, явно
отложившее файл: «объектное хранилище, лимиты размера/типа и отдача файла
образуют отдельную инфраструктурную фичу»). Организатору нужен сторонний
хостинг, чтобы приложить к своему турниру PDF или картинку, — а ссылка на
чужой сервис живёт ровно до тех пор, пока тот жив.

`docs/adr/0017-deferred-debt-porting-order.md` (п. 4.4) называет объектное
хранилище пунктом с собственной инфраструктурной ADR внутри `0042`. Спека
`0042-account-mail-and-files` (FR-30..FR-38, NFR-4, NFR-9) формулирует
требования — регламент и эмблема турнира загружаются файлом, оба
взаимоисключающе со своей ссылкой (решение 10 спеки). Эта ADR фиксирует,
как хранилище устроено.

## Решение

### 1. Порт, не конкретный сервис

Домен (модуль `tournament`) не знает, где физически лежит файл. Порт в
`server/pkg/filestore`:

```go
type Store interface {
    Put(ctx context.Context, r io.Reader, meta Meta) (id string, err error)
    Open(ctx context.Context, id string) (io.ReadCloser, Meta, error)
    Delete(ctx context.Context, id string) error
}

type Meta struct {
    ContentType string
    Size        int64
}
```

Домен хранит только `id` (случайный, не путь на диске — путь остаётся
деталью адаптера) плюс имя и размер файла для интерфейса.

### 2. Единственный адаптер — локальный том

Реализуется один адаптер, `filestore/local`: файл кладётся на диск под
случайным UUID-именем в каталог, заданный `FILE_STORAGE_DIR`. Docker-том
переживает пересборку контейнера.

Отклонено на этом этапе:

- **S3-совместимое хранилище (MinIO в compose)** — лишний сервис в
  инфраструктуре ради пары файлов на турнир (регламент + эмблема, ни
  галереи, ни пользовательских загрузок). Ближе к продовому развёртыванию,
  но плата за это — ещё один контейнер, ещё один набор кредов, ещё один
  пункт в `docker-compose`, которого сегодняшний объём данных не
  оправдывает.
- **Оба адаптера сразу** — вдвое больше кода и тестов без потребителя
  второго. Порт существует ровно для того, чтобы второй адаптер
  добавился без правки домена, когда реальная нужда (масштабирование за
  один инстанс, миграция в облако) появится — задача тогда одна: написать
  `filestore/s3`, конфигурацией выбрать реализацию.

`nil`-`Store` — легальное состояние: хранилище не настроено
(`FILE_STORAGE_DIR` пусто), домен отвечает `ErrStorageUnavailable` на
загрузку, а профиль турнира продолжает работать на ссылках (NFR-4).
Разработка и тесты не требуют тома по умолчанию.

### 3. Тип файла определяется по содержимому, не по заявленному

Загружающий передаёт `content_type` — но решение принимает `Sniff` (в
`pkg/filestore`): проверка бинарной сигнатуры против белого списка
(PDF, PNG, JPEG, WebP). Заявленный тип используется только на BFF для
ранней отбраковки без похода на сервер; окончательное решение и то, с
каким `Content-Type` файл будет отдаваться, — по сигнатуре.

Причина — эмблема отдаётся с **нашего** домена (в отличие от сегодняшней
ссылки на чужой хостинг). Подмена заявленного типа не должна превращать
загрузку «картинки» в размещение произвольного документа на нашем origin.
По той же причине эмблема принимает только растровые форматы — **SVG
исключён явно** (спека `0042`, решение 11): это исполняемый документ
(скрипты, внешние ссылки внутри разметки), и его безопасная отдача
требует либо санитайзинга контента, либо отдельного домена для
пользовательского содержимого — отдельная работа, не сторона объектного
хранилища. Векторная эмблема остаётся доступна ссылкой.

Отдача файла добавляет заголовок `X-Content-Type-Options: nosniff` —
браузер не переопределяет тип, определённый сервером.

### 4. Пороги и белый список — по виду файла, не общие

`tournament.domain.FilePolicy{AllowedTypes, MaxBytes}` задаётся отдельно
на регламент (PDF, до 10 МБ) и на эмблему (PNG/JPEG/WebP, до 5 МБ).
Значения по умолчанию берутся из конфигурации (`REGULATIONS_MAX_BYTES`,
`EMBLEM_MAX_BYTES`); сами списки допустимых типов — константы политики
модуля, конфигурацией не переопределяются: их расширение требует поддержки
в `Sniff` и осмысленного решения о безопасности отдачи, а не строки в
`.env`.

### 5. Порядок put→update→delete без распределённой транзакции

Диск и PostgreSQL не участвуют в одной транзакции. Порядок операции
замены/удаления файла фиксирован:

1. `filestore.Put` нового файла (если загрузка);
2. `UPDATE tournament.tournaments` — переключение ссылки на новый `id`
   (или на пустое значение при удалении);
3. `filestore.Delete` прежнего объекта.

При сбое между шагами 1 и 2 остаётся лишний неиспользуемый файл на диске
(осиротевший объект) — не потеря данных, домен по-прежнему ссылается на
целый файл. При сбое между 2 и 3 — та же ситуация, прежний объект просто
не удалён. **Обратный порядок недопустим**: удаление прежнего файла до
подтверждённой записи нового id могло бы на мгновение (или при сбое —
навсегда) оставить в БД ссылку на уже удалённый объект.

Автоматическая уборка осиротевших объектов этой ADR не заводится — при
объёме «один регламент и одна эмблема на турнир» цена ручной уборки
(при необходимости — прямой доступ к тому) ниже цены фоновой сборки
мусора. Пересмотреть, если хранилище получит больше потребителей
(«Вне скоупа» спеки `0042` явно не расширяет состав).

### 6. Отдача — публичный HTTP-хендлер, не Connect RPC

Файлы отдаются обычным `GET /files/{id}` на том же `http.ServeMux`, что и
Connect-сервисы (не через protobuf `bytes` в ответе — это сделало бы
каждый показ страницы с эмблемой недёшевым RPC). Хендлер публичен без
токена: и регламент, и эмблема турнира — публичные данные (как и их
ссылочные предшественники). Браузер клиента ходит в BFF, а не напрямую в
Go-сервер (ADR 0001); `app/api/files/[id]/route.ts` проксирует поток,
сохраняя `Content-Type` и `X-Content-Type-Options: nosniff`.

## Область действия

Первый и единственный потребитель порта — модуль `tournament`
(регламент + эмблема, спека `0042`). Другие модули к `filestore` не
обращаются. Расширение состава (фотографии бойцов, вложения заявок,
галереи) — отдельная фича с собственной оценкой, не молчаливое повторное
использование этого порта без пересмотра лимитов и владения данными.

## Последствия

- Новый пакет `server/pkg/filestore` (порт + `Sniff` + адаптер `local`),
  без внешних зависимостей сверх стандартной библиотеки.
- `docker-compose` получает именованный том под `FILE_STORAGE_DIR`.
- Резервный путь без хранилища (`nil`-`Store`) обязателен к тестированию:
  профиль турнира не должен падать при старте без смонтированного тома.
- Второй адаптер (S3 или любой другой) — будущая задача с известной ценой:
  реализовать `Store`, ничего не меняя в `tournament/service` или в proto.

## Альтернативы

- **MinIO/S3 сейчас** — отклонено, см. п. 2.
- **Хранить файл в PostgreSQL (`bytea`)** — отклонено: раздувает бэкапы
  БД бинарными данными, которые не участвуют в реляционных запросах, и не
  даёт ничего сверх того, что уже даёт файл на диске.
- **Доверять заявленному `content_type` при отдаче** — отклонено, см. п.
  3: подмена типа на пользовательском домене — известный класс уязвимости
  (content sniffing/XSS через якобы-картинку).
- **Принимать SVG как обычный растровый формат** — отклонено, см. п. 3;
  требует отдельного решения о санитайзинге или изоляции домена, не входит
  в эту ADR.
