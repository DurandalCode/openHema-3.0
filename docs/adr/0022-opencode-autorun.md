# ADR 0022: Автозапуск opencode по карточкам задач

- Статус: принято
- Дата: 2026-08-30

## Контекст

ADR 0021 даёт формат самодостаточных карточек задач
(`docs/specs/NNN-*/tasks/*.md`) и скилл `implement-task` для opencode, но
хендофф между Claude и локальной моделью — ручной: человек сам
переключается в отдельную opencode-сессию и указывает ей карточку.

Пользователь хочет, чтобы Claude сам запускал opencode по уже
сгенерированным карточкам. Локально установлен CLI `opencode` (проверено:
`opencode run [message]` — headless однократный прогон с флагами `--model
provider/model`, `--dir <path>`, `--auto` для автоподтверждения
permission-запросов). Это даёт техническую возможность, но меняет
риск-профиль по сравнению с 0021: Claude запускает внешний процесс,
который пишет в файлы и гоняет shell-команды **без интерактивного
подтверждения** — `--auto` обязателен для headless-режима, иначе процесс
зависнет на первом же permission-промпте, ожидая ответа, которого некому
дать.

Это отдельное архитектурное решение, а не расширение 0021 "бесплатно" —
фиксируется отдельной ADR, ссылающейся на 0021.

## Решение

### Скилл `run-local-tasks` (только Claude)

Единственная точка автозапуска — `.claude/skills/run-local-tasks/SKILL.md`.
Берёт pending-карточки со `status: pending`, `requires: local`, идёт по ним
последовательно с учётом `depends_on`, для каждой:

1. Заводит изолированный `git worktree` (`.claude/worktrees/local-<T#>-<slug>`,
   ветка `local/<T#>-<slug>`) от текущего HEAD рабочей ветки. В отличие от
   параллельных треков `tdd-cycle` (которые используют `Agent` с
   `isolation: "worktree"` — это Claude-субагенты), здесь worktree заводится
   и убирается вручную через `git worktree add/remove`, потому что
   исполнитель — внешний процесс (`opencode`), не Claude-субагент.
2. Запускает `opencode run --dir <worktree> --model "$OPENCODE_LOCAL_MODEL"
   --auto "<инструкция с путём к карточке, через implement-task>"`.
3. **Не доверяет самоотчёту opencode.** После завершения процесса Claude
   сам проверяет: карточка реально помечена `status: done`; `git diff`
   worktree трогает только файлы, названные в Red/Green/Boundaries
   карточки; acceptance-команда карточки, прогнанная Claude независимо —
   зелёная. Это verification-gate — обязателен, не опционален.
4. Только после прохождения gate — коммит (если ещё не закоммичено),
   `git merge` ветки карточки в рабочую ветку, `git worktree remove` +
   `git branch -d` за собой (та же дисциплина уборки, что в `tdd-cycle`).

### `OPENCODE_LOCAL_MODEL` — переменная окружения, не конфиг репозитория

Модель (`provider/model`) не хардкодится в скилле и не коммитится (правило
6 `AGENTS.md`) — у каждого разработчика своя локальная модель. Скилл читает
`$OPENCODE_LOCAL_MODEL`; если переменная не задана — останавливается с
понятной ошибкой, не пытается угадать модель или использовать
дефолт-провайдер opencode (который может оказаться облачным).

### Stop-on-first-failure

Один вызов скилла проходит **все** pending-карточки подряд автономно (без
паузы между ними — это осознанный выбор в пользу автономности), но
останавливается на первой же карточке, провалившей verification-gate.
Worktree/ветка провалившейся карточки **не удаляются** — остаются для
разбора. Последующие pending-карточки не трогаются. Не пытаться
"продавить" мерж силой (`--no-verify`, force) — та же дисциплина, что
`tdd-cycle` требует при конфликтах параллельных треков.

## Обоснование

- `--auto` — единственный способ headless-прогона, но сам по себе не даёт
  никаких гарантий; изоляция в worktree + verification-gate перед мержем —
  это и есть механизм снижения риска, а не его отсутствие.
- Verification силами Claude (а не доверие статусу карточки, который
  проставляет сама локальная модель) — та же логика, что в `implement-task`
  (ADR 0021): слабой/локальной модели нельзя доверять самооценку результата.
- Остановка на первом провале ограничивает blast radius одной карточкой —
  без этого одна плохая карточка могла бы каскадно испортить контекст для
  всех следующих (например, они опираются на её файлы через `depends_on`).
- Явная переменная окружения вместо угадывания модели — предотвращает
  случайный прогон на не той модели (в т.ч. случайно облачной).

## Последствия

- `AGENTS.md`/`docs/specs/README.md` перечисляют `run-local-tasks` рядом с
  `decompose-tasks`/`implement-task`.
- Параллельный прогон нескольких карточек одновременно — вне скоупа этой
  ADR; при необходимости — отдельный инкремент.
- Автоматический повторный прогон провалившейся карточки после её
  перегенерации `decompose-tasks` — остаётся ручным вызовом скилла заново,
  не автоматизируется.
- Сама настройка `OPENCODE_LOCAL_MODEL` и провайдера в opencode под
  конкретный рантайм (LM Studio/Ollama) — скилл `setup-local-model`, чтобы
  это не было знанием одного человека в команде.
