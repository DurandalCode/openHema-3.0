# ADR 0021: Карточки задач для локальной модели

- Статус: принято
- Дата: 2026-08-30

## Контекст

Проект AI-first (`AGENTS.md`): значительную часть кода пишут агенты, процесс
SDD (ADR 0008) + TDD (ADR 0009) рассчитан на исполнителя, который сам держит
в контексте конституцию проекта (`AGENTS.md` и вложенные), сам ориентируется
в конвенциях модулей и сам принимает мелкие архитектурные решения по ходу
`tasks.md`.

Часть реализации предполагается отдавать локальной модели (opencode +
Qwen), работающей без доступа к большому контексту и с меньшей надёжностью
следования неявным конвенциям, чем у Claude. Прямая выдача такой модели
`tasks.md` "как есть" — риск: она либо тратит контекст на самостоятельный
поиск конвенций (и промахивается), либо игнорирует часть неявных требований
конституции.

Требование пользователя: авторство спеки (`spec.md`/`plan.md`/`tasks.md`)
не должно зависеть от того, кто будет реализовывать — процесс SDD один и тот
же для обоих контуров. Разница должна проявляться только на шаге
реализации.

## Решение

Между `tasks.md` и `code` вводится необязательный шаг **карточки** —
раскладывание уже готового `tasks.md` на отдельные самодостаточные файлы
`docs/specs/NNN-*/tasks/<T#>-<slug>.md`, по одной карточке на задачу.
Карточка содержит весь нужный для реализации контекст инлайном (пути,
релевантные куски существующего кода, точный тест, критерий готовности) —
исполнителю не нужно ничего искать по репозиторию сверх того, что названо в
самой карточке.

Шаг вызывается **по требованию** (когда решили отдать конкретные задачи
локальной модели), не автоматически при каждом `tasks.md`. Для Claude
ничего не меняется — он как и раньше может реализовывать прямо от
`tasks.md` через `tdd-cycle`.

### Формат карточки

Источник истины формата — `docs/specs/_templates/task-card.md`.
Frontmatter: `task` (id из `tasks.md`, напр. `T3`), `feature` (путь к
спеке), `status: pending|done`, `requires: local|claude`, `depends_on`.
Тело: Цель → Контекст (инлайненный код) → Red (тест) → Green (реализация)
→ Acceptance (точная команда) → Boundaries (что не трогать).

### Два новых скилла, без зеркалирования

- `.claude/skills/decompose-tasks/SKILL.md` — только Claude. Читает
  `tasks.md`, для каждой невыполненной задачи решает `requires: local`
  (типовая пара тест→код на известном слое, зеркалящая существующий
  паттерн) или `requires: claude` (новый модуль, изменение proto,
  миграции со структурными решениями, что-то, тянущее на отдельный ADR).
  Для `local`-задач собирает контекст и пишет карточку; для `claude`-задач
  карточку не создаёт — они остаются обычными пунктами `tasks.md`.
- `.opencode/skill/implement-task/SKILL.md` — только opencode. Берёт ровно
  одну карточку со `status: pending`, работает исключительно с её
  содержимым (не читает `AGENTS.md`/`spec.md`/`plan.md`/остальные задачи),
  прогоняет red→green→refactor и acceptance-команду дословно из карточки.
  При неполноте/противоречии инструкций — останавливается и эскалирует, не
  импровизирует и не выходит за объявленный в карточке scope.

Это осознанное исключение из правила "скиллы SDD-цикла зеркалятся между
`.claude/skills/` и `.opencode/skill/`" (`CLAUDE.md`): `decompose-tasks`
требует сильную модель и полный контекст конституции, `implement-task`
рассчитан только на локальный контур и намеренно лишён такого контекста.

## Обоснование

- Разделение "кто пишет спеку" и "кто реализует" не смешивается — карточки
  строятся из уже готового `tasks.md`, спека не знает про исполнителя.
- Самодостаточность карточки — единственный способ дать слабой модели
  результат, сопоставимый по качеству со следованием конституции, не
  рассчитывая, что она сама удержит `AGENTS.md` в контексте.
- On-demand триггер не тратит токены Claude на декомпозицию, когда фичу
  реализует сам Claude.
- Явное разделение задач на `requires: local`/`requires: claude` не даёт
  локальной модели попасть на архитектурные решения, которые дорого
  переигрывать (по аналогии с логикой ADR 0008 про spec/plan).

## Последствия

- `docs/specs/NNN-*/tasks/` — новая опциональная поддиректория спеки;
  `tasks.md` остаётся источником истины статусов, карточки — производный,
  перегенерируемый артефакт.
- `tdd-cycle` (Claude) при столкновении с уже отмеченной как `done`
  карточкой пропускает задачу; карточки `requires: claude` доделывает как
  обычный пункт `tasks.md`.
- Если единый `implement-task` окажется слишком широким для конкретной
  локальной модели — дробление по слоям (server/web) выносится отдельным
  инкрементом, не в рамках этой ADR.
- Автозапуск opencode по карточкам из Claude Code (без ручного
  переключения в opencode-сессию) — отдельная ADR 0022, не часть этой.
