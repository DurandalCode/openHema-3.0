# Деплой и инфраструктура

> Прикидки под Yandex Cloud, зафиксированные в разговоре 2026-08-30. Числа —
> оценка по архитектуре и заявленному масштабу, не измерение с боевого
> турнира. Уровни «региональный»/«крупный» не проверены на практике — после
> первого такого турнира стоит вернуться и поправить по факту (метрики CPU/
> RAM/подключений).

## Архитектурное ограничение: один инстанс

`pkg/livebus` (SSE-пуш живого табло, ADR 0012) спроектирован **только под
один инстанс** приложения — сигнал не пересекает границы процесса.
Горизонтальное масштабирование потребовало бы внешнего fan-out (Redis/NATS)
или перехода на полноценную событийную шину — это осознанно отложено
(ADR 0012, «Когда вводить полноценную событийную шину»).

Следствие для инфры: **Kubernetes не нужен**. Один инстанс — это один
`docker-compose` (как в корне репо: postgres + migrate + server + web) на
одной ВМ. Managed-кластер добавил бы стоимость control plane и
эксплуатационную сложность без выгоды — оркестрировать нечего, реплик нет.

## Оценка по масштабу турнира

| Масштаб | Участники + зрители табло одновременно | ВМ (Compute Cloud) | Диск | Postgres | Файлы (регламент/эмблема) |
|---|---|---|---|---|---|
| **Локальный клуб** | до ~50 | burstable `standard-v3`, 2 vCPU (доля 20%), 2–4 ГБ RAM | 20–30 ГБ сетевой SSD | self-hosted в том же compose | локальный том (`FILE_STORAGE_DIR`) |
| **Региональный** (не проверено) | ~50–200 | 2 vCPU (доля 50–100%) или 4 vCPU (доля 20%), 4–8 ГБ RAM | 30–50 ГБ SSD | self-hosted, тот же compose | локальный том, размер тот же (файлы не растут с числом зрителей) |
| **Крупный/федеральный** (не проверено) | 200+ | 4 vCPU (доля 100%), 8 ГБ RAM | 50 ГБ SSD | self-hosted пока хватает объёма/нагрузки; managed PostgreSQL — только если понадобится HA/бэкапы уровня SLA | локальный том; Object Storage стоит завести, если файлов станет много одновременно (несколько параллельных турниров/архив за годы) |

Общее для всех уровней:

- **Managed PostgreSQL не нужен** ни на одном уровне из перечисленных —
  объём данных одного турнира (заявки/номинации/счёт боёв) на порядки
  меньше, чем оправдывает управляемую БД. Self-hosted в том же compose —
  дешевле и уже так устроено.
- **Object Storage не нужен для файлов** на текущем масштабе — регламент
  ≤10 МБ, эмблема ≤5 МБ на турнир (спека 0042). Нужен только для бэкапов
  (см. ниже) и то не файлового хранилища, а дампов БД.
- **Без балансировщика/autoscaling** — один инстанс, точка входа — один
  статический публичный IP + reverse proxy на самой ВМ (TLS).
- **Между турнирами — стоп ВМ.** Compute Cloud считает по секундам,
  выключенная ВМ не тарифицируется по CPU/RAM — платите только за диск и IP.

## Бэкапы

Два независимых уровня, оба нужны:

1. **Снапшот диска ВМ** — для восстановления окружения целиком («сервер
   сломался, поднимаю с нуля»). Расписание: снять перед турниром и после.
2. **`pg_dump` после турнира** — портируемый архив данных, независимый от
   жизни ВМ (которая между турнирами гасится). Восстанавливается в любой
   Postgres 16+, можно поднять локально или отдать организатору отдельно.

```bash
# дамп БД (custom format, сжатый)
docker compose exec postgres pg_dump -U hema -d hema -Fc -f /tmp/dump.pgdump
docker compose cp postgres:/tmp/dump.pgdump ./dumps/hema-$(date +%F).pgdump

# файлы турнира (регламент/эмблема) — дамп БД на них ссылается
tar czf ./dumps/hema-files-$(date +%F).tar.gz -C "$FILE_STORAGE_DIR" .

# заливка в Yandex Object Storage (S3-совместимый API)
aws --endpoint-url=https://storage.yandexcloud.net s3 cp \
  ./dumps/hema-$(date +%F).pgdump s3://hema-backups/
aws --endpoint-url=https://storage.yandexcloud.net s3 cp \
  ./dumps/hema-files-$(date +%F).tar.gz s3://hema-backups/
```

Дампы **не хранить только на ВМ** — она гасится между турнирами, диск
теоретически может быть пересоздан. Object Storage — копейки за ГБ/месяц,
не зависит от жизни ВМ.

Турниры редкие и запускаются вручную — cron/systemd-timer заводить не
нужно, это последний шаг ритуала «закрыли турнир → сняли дамп → выключили
ВМ».

## Почта — Yandex Cloud Postbox

Транзакционные письма (подтверждение email, восстановление пароля — спеки
0037/0042) — через **Yandex Cloud Postbox**, не через сторонний SMTP.

- **SMTP-хост**: `postbox.cloud.yandex.net`, порт `587` (STARTTLS) или `465`
  (SMTPS) — подставляется в `SMTP_HOST`/`SMTP_PORT` из `.env.example`.
- **Аутентификация**: сервис-аккаунт с ролью `postbox.sender`, логин/пароль —
  ID и секрет API-ключа → `SMTP_USERNAME`/`SMTP_PASSWORD`.
- **Верификация домена обязательна** до отправки — разовая настройка на
  стороне Postbox, делается заранее, до переезда на прод (иначе `SMTP_FROM`
  будет настроен, а письма — отбрасываться).
- Есть delivery simulator для проверки без реальных адресатов.
