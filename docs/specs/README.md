# Спецификации фич (Spec-Driven Development)

> Процесс: см. `docs/adr/0008-spec-driven-development.md`.
> TDD-цикл: см. `docs/adr/0009-tdd-workflow.md`.

Каждая нетривиальная фича проходит цикл **spec → plan → tasks → code**.

## Структура

```
docs/specs/
  README.md                       этот файл
  _templates/                     шаблоны — источник истины формата
    spec.md                       ЧТО и ЗАЧЕМ (без технологий)
    plan.md                       КАК (proto, модули, слои, БД, тесты)
    tasks.md                      упорядоченный TDD-чеклист
  NNN-<kebab-feature>/            папка одной фичи
    spec.md
    plan.md
    tasks.md
```

Нумерация `NNN-<kebab-feature>` — сквозная, три цифры, kebab-case имя. Пример
формата — `0000-healthcheck`; реальные фичи нумеруются с `0001`.

## Процесс

1. **spec** — заполнить `spec.md` из шаблона. Проговорить проблему, акторов,
   сценарии, критерии приёмки (Given/When/Then). Всё неясное — в раздел
   `[NEEDS CLARIFICATION]`. Не переходить дальше, пока остались нерешённые
   критичные вопросы.
2. **plan** — заполнить `plan.md`: как ложится на `proto`, server-модули и их
   слои, PG-схему, web-слои (FSD + BFF), какие тесты по пирамиде (ADR 0003).
3. **tasks** — разложить `plan.md` на упорядоченный TDD-чеклист (`tasks.md`):
   каждая задача = слой/файл + пара «тест → код».
4. **code** — выполнять `tasks.md` по TDD-циклу red → green → refactor.

## Инструменты

- Скилл `write-spec` — создаёт `docs/specs/NNN-*/` из шаблонов и ведёт
  заполнение.
- Команда `/spec <краткое описание фичи>` — быстрый запуск SDD-цикла из чата.
- Скилл `tdd-cycle` — прогон задач из `tasks.md` по red-green-refactor.

## Когда спека нужна

Обязательна: новый модуль/фича, нетривиальный RPC, кросс-слойное изменение
контрактов. Не нужна: рефактор, баг-фикс, косметика — им хватает инкремента с
тестами.

Видимое изменение UI ровно одно — название этапа над составом групп на админском и публичном экранах (FR-11); создание/удаление/переименование этапов, второй тип этапа (сетка), правила посева и пресеты — планы 0018–0020 |
| 0018 | playoff-bracket     | done    | Плейофф-сетка с ручным посевом — второй шаг плана ADR 0014. Появляется **второй тип этапа** (`bracket`): admin добавляет номинации этап-сетку, задавая размер (4/8/16/32) и флаг боя за 3-е место, и **вручную** сажает бойцов в слоты первого круга (автоматический отбор по итогам групп — 0019). Пустой слот законен: при фиксации он означает **бай** — соперник проходит дальше без боя, каскадом (6 бойцов в сетке на 8 без фиктивных участников). **Контейнер боёв — половина круга, а не круг** (уточнение к ADR 0014 §3: до финала половины сетки не пересекаются, поэтому верхнюю и нижнюю можно вести параллельно на двух площадках); финал и бой за 3-е место — отдельные контейнеры на одну пару. Ведение, арена, текущий бой, табло и таймер (0011/0013/0015) переиспользуются **без единой правки** — круг для них неотличим от группы. **Дерево слотов не хранится**: персистентен только посев (членство `pool_members` + номер слота), всё остальное — чистая функция `ResolveBracket(конфиг, посев, завершённые бои)` по образцу `ComputeStandings`; бой материализуется, только когда известны обе стороны (ADR 0014 §4 — модуль `bout` не получает TBD-участников). Побочное следствие «посев = членство»: реконсиляция ростера (0007) перестаёт трогать **зафиксированные** сетки — иначе снятие бойца с турнира молча переигрывало бы плейофф (пара стала бы баем, несыгранный бой исчез). Ничья в сетке запрещена (правило этапа, не боя); пересмотр результата обратим, **пока следующий бой победителя не начат** — тогда продвижение снимается и неначатый бой следующего круга исчезает. Попутно закрываются два долга 0017: адресация раскладки переезжает с номинации на **этап** (`stage_id` в RPC, этапная навигация в админке), а `bout.ReplaceForNomination` → `ReplaceForPools` — номинационный replace со вторым этапом стёр бы бои первого. Вне скоупа: селекторы/переходы и параллельные ветки (0019), конструктор и пресеты (0020), протокол призёров и `ACTIVE`/`FINISHED` номинации (0021), double elimination, переименование «пул» → «контейнер боёв» |
| 0019 | stage-transitions   | draft   | Переходы между этапами — третий шаг плана ADR 0014. У этапа появляется **правило отбора** (источник → селектор → метод раскладки): источник — ростер номинации либо другой групповой этап той же номинации; селекторы — «все», «места X–Y каждой группы», «места X–Y сводного порядка» (верхняя граница может быть открытой); метод выводится из типа целевого этапа и организатору не предлагается — змейка 0009 в группы, классический посев «1×N» в сетку. Вводится **сводный порядок этапа** — сквозное упорядочивание участников всех групп («место в группе, затем критерии 0016»), без новых тай-брейков и без нормировки на размер группы (известное искажение, NFR-2). **Параллельные ветки выражаются общим источником** (позиция выводится из источника, вручную не задаётся) — отсюда двойной плейофф и двойная сетка групп одним механизмом; пересечение селекторов веток — ошибка схемы, непокрытые бойцы — законный исход, но превью показывает и то, и другое. Формирование — **явное обратимое действие admin** с превью («Группа 2, место 1 → слот 3», вместимость, предупреждение о недоигранном источнике — формировать при этом можно); подтверждение заполняет состав и оставляет этап в черновике (фиксация и бои — прежними действиями), повторное формирование поверх непустого состава отклоняется, расформирование = существующий сброс состава, а сразу после формирования доступно «Отменить» (новый вид undo-снапшота `build`). **Дележ мест на границе отбора** останавливает формирование и разрешается организатором вручную (ADR 0014 §7 — новых тай-брейков система не выдумывает). Групповой этап теперь создаётся и явным действием, с числом групп как параметром схемы (ADR 0014 §1a — без него пресет 0020 бессмысленен); авто-этап 0017 остаётся. Всё в модуле `stage` (ADR 0014 §8), ядро — чистые функции по образцу `ComputeStandings`/`ResolveBracket`; `bout`/`nomination`/`fighter`/`arena` не меняются вовсе. Вне скоупа: жеребьёвка как метод раскладки (недетерминирована), конструктор схемы и пресеты (0020), протокол призёров и `ACTIVE`/`FINISHED` (0021), отбор по итогам сетки и double elimination, слияние веток, разведение одногруппников по половинам сетки |
