# Спецификации фич (Spec-Driven Development)

> Процесс: см. `docs/adr/0008-spec-driven-development.md`.
> TDD-цикл: см. `docs/adr/0009-tdd-workflow.md`.

Каждая нетривиальная фича проходит цикл **spec → plan → tasks → code**.

## Структура

```
docs/specs/
  README.md                       этот файл
  _templates/                     шаблоны — источник истины формата
    spec.md                       ЧТО и ЗАЧЕМ (без технологий)
    plan.md                       КАК (proto, модули, слои, БД, тесты)
    tasks.md                      упорядоченный TDD-чеклист
  NNN-<kebab-feature>/            папка одной фичи
    spec.md
    plan.md
    tasks.md
```

Нумерация `NNN-<kebab-feature>` — сквозная, три цифры, kebab-case имя. Пример
формата — `0000-healthcheck`; реальные фичи нумеруются с `0001`.

## Процесс

1. **spec** — заполнить `spec.md` из шаблона. Проговорить проблему, акторов,
   сценарии, критерии приёмки (Given/When/Then). Всё неясное — в раздел
   `[NEEDS CLARIFICATION]`. Не переходить дальше, пока остались нерешённые
   критичные вопросы.
2. **plan** — заполнить `plan.md`: как ложится на `proto`, server-модули и их
   слои, PG-схему, web-слои (FSD + BFF), какие тесты по пирамиде (ADR 0003).
3. **tasks** — разложить `plan.md` на упорядоченный TDD-чеклист (`tasks.md`):
   каждая задача = слой/файл + пара «тест → код».
4. **code** — выполнять `tasks.md` по TDD-циклу red → green → refactor.

## Инструменты

- Скилл `write-spec` — создаёт `docs/specs/NNN-*/` из шаблонов и ведёт
  заполнение.
- Команда `/spec <краткое описание фичи>` — быстрый запуск SDD-цикла из чата.
- Скилл `tdd-cycle` — прогон задач из `tasks.md` по red-green-refactor.

## Когда спека нужна

Обязательна: новый модуль/фича, нетривиальный RPC, кросс-слойное изменение
контрактов. Не нужна: рефактор, баг-фикс, косметика — им хватает инкремента с
тестами.

| 0018 | playoff-bracket     | done (изменён 0019/0020) | Плейофф-сетка с ручным посевом — второй шаг плана ADR 0014. Появляется **второй тип этапа** (`bracket`): admin добавляет номинации этап-сетку, задавая размер (4/8/16/32) и флаг боя за 3-е место, и **вручную** сажает бойцов в слоты первого круга (автоматический отбор по итогам групп — 0019). Пустой слот законен: при фиксации он означает **бай** — соперник проходит дальше без боя, каскадом (6 бойцов в сетке на 8 без фиктивных участников). **Контейнер боёв — половина круга, а не круг** (уточнение к ADR 0014 §3: до финала половины сетки не пересекаются, поэтому верхнюю и нижнюю можно вести параллельно на двух площадках); финал и бой за 3-е место — отдельные контейнеры на одну пару. Побочное следствие «посев = членство»: реконсиляция ростера (0007) перестаёт трогать **зафиксированные** сетки — иначе снятие бойца с турнира молча переигрывало бы плейофф (пара стала бы баем, несыгранный бой исчез). Попутно закрываются два долга 0017: адресация раскладки переезжает с номинации на **этап** (`stage_id` в RPC, этапная навигация в админке), а `bout.ReplaceForNomination` → `ReplaceForPools` — номинационный replace со вторым этапом стёр бы бои первого. Вне скоупа: селекторы/переходы и параллельные ветки (0019), конструктор и пресеты (0020), протокол призёров и `ACTIVE`/`FINISHED` номинации (0021), double elimination, переименование «пул» → «контейнер боёв» |
