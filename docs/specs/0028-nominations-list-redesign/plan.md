- Статус: ready
- Дата: 2026-08-14
- Спека: `./spec.md`

## Обзор решения

Инкремент **целиком в `/web`**, без единой строки в `/proto` и `/server`:
`/admin/nominations` пересобирается из примитивов 0022/0023 по правилам
0024–0027 (`PageHeader`, `TableHead`/`TableRow`, модалки вместо раскрытых
форм, тосты через `shared/lib/toast`, `ConfirmDialog` на необратимое,
скелетоны) и получает **сводку схемы в строке**, вычисляемую чистой функцией
из уже существующего списка этапов номинации (`GET /api/nominations/[id]/
stages`, спеки 0018–0020). Этапы запрашиваются по одной номинации через
`useQueries` **без периодического обновления** — схема, в отличие от досок
площадок (0027), холодная.

Четыре содержательных сдвига помимо визуала:

1. **Разрушительное действие получает подтверждение.** Удаление номинации
   сегодня выполняется одним кликом (spec п.1 «Проблема»), а сервер его
   ничем не гейтит — переводим на `ConfirmDialog` с `confirmWord`
   (0023, FR-7) и перечислением потерь. Серверный гейт и каскад — вне
   скоупа по решению пользователя (spec «Вне скоупа»).
2. **Мёртвый вызов убирается.** `getPoolLayoutStatusRequest` +
   `usePoolLayoutStatus` + ключ `poolLayoutStatus` зовут ручку
   `/api/nominations/[id]/pool-status`, удалённую в 0017 (PR #23,
   `git log --diff-filter=D`): каждая строка списка делает 404-запрос,
   бейдж раскладки не рендерится никогда, `hasDistributedFighters` всегда
   `false`. Удаляем клиентскую половину целиком (spec FR-17).
3. **Гейт «Открыть приём» переезжает на статус номинации.** После п.2
   единственный клиентский гейт — `status ∈ {ACTIVE, FINISHED}` (spec
   FR-13); отказ по распределённым бойцам/автоматическому закрытию остаётся
   за сервером (0012, FR-4) и переводится на русский **по HTTP-статусу
   ответа (409), а не сопоставлением текста** — сообщение приходит из
   Go-домена (`nomination: registration cannot be reopened`), сравнивать
   строки было бы хрупко (в 0027 строку можно было переписать в самой
   ручке, здесь — нельзя без правки сервера, NFR-1).
4. **Схема номинации становится видимой из списка.** `ListStages` отдаёт и
   этапы, и диагностику схемы (`issues`, 0020, FR-8) одним ответом —
   сводка и счётчик ошибок считаются из него чистыми функциями, без второго
   запроса и без своей копии правил диагностики.

## Контракты (proto)

**Изменений нет.** Всё, что нужно экрану, уже есть в контракте:

| Что нужно экрану | Существующий RPC | Спека |
| --- | --- | --- |
| список номинаций | `NominationPublicService.ListNominations` | 0003 |
| создание/правка/удаление | `CreateNomination` / `UpdateNomination` / `DeleteNomination` | 0003 |
| порядок | `ReorderNominations` | 0003 |
| приём заявок | `CloseRegistration` / `ReopenRegistration` | 0012 |
| схема этапов + диагностика | `StageAdminService.ListStages` (`stages` + `issues`) | 0018/0020 |

`make generate` не требуется. Запись «Номинации → новый API нужен? нет» в
`docs/design-sync.md` остаётся верной (как в 0027, в отличие от 0025/0026).

## Server (модули и слои)

**Изменений нет.** `modules/nomination` и `modules/stage` не трогаются:
домен, сервис, репозиторий, миграции и api-слой остаются как есть. В
частности, `Service.Delete` остаётся без гейтов, а `ErrCannotReopen`
(0012) — единственным арбитром переоткрытия приёма.

## Web (FSD + BFF)

### BFF (Route Handlers)

**Изменений нет.** Используются как есть:

- `app/api/nominations/route.ts` (`GET`/`POST`), `.../[id]/route.ts`
  (`PUT`/`DELETE`), `.../reorder/route.ts`;
- `.../[id]/close-registration/route.ts`, `.../[id]/reopen-registration/
  route.ts` — 409 на `FailedPrecondition` уже есть (`lib/grpc/errors.ts`);
- `.../[id]/stages/route.ts` (`GET`) — отдаёт `stages` + `issues`, admin-only.

Удалённая в 0017 ручка `pool-status` **не восстанавливается** (spec FR-17).

### `shared/`

Изменений не требуется — примитивы берутся как есть: `ui/{page-header,
table-head,table-row,dialog,confirm-dialog,input,label,textarea,button,badge,
tag,empty-state,skeletons,tooltip}`, `lib/{toast,cn}`. Строка номинации
укладывается в существующее API `TableRow` (`cells[].sub` для описания и
подписи схемы, `cells[].tags` для статуса приёма, `node`-слот из 0025 — для
составных ячеек: стрелок порядка, ссылки на регламент и группы действий).

### `entities/nomination/`

- `lib/types.ts` — добавляется чистая `nominationStatusTag(status)` →
  `{ label: "Приём открыт" | "Приём закрыт" | "Бои идут" | "Завершена";
  tone }` (spec FR-4). Существующая `nominationStatusLabel` («приём заявок
  открыт», фразовая форма) остаётся — её зовут другие экраны; вторая
  функция нужна потому, что в колонке таблицы нужна короткая форма, а не
  предложение.

### `entities/stage/`

- `lib/labels.ts` — добавляется экспортируемая
  `stageSchemaSummary(stages: Stage[]): string` (spec FR-5):
  - уровни — существующая `groupStagesByLevel` (0019, FR-10): позиции по
    возрастанию, внутри уровня — по названию;
  - подпись этапа — «Группы (N)» / «Сетка (N)», параллельные ветки уровня
    через « + », уровни через « → »;
  - `""` (пусто) — когда схемы фактически нет: этапов нет вовсе **либо**
    единственный этап — групповой без заданного числа групп (авто-этап
    0017 FR-4 / 0019 FR-9). Подпись «Схема не задана» — на стороне UI, а не
    внутри функции (в спеках 0031/0032 её место может отличаться).
  - приватная `formatStageSpecSummary` (пресеты, 0020) и новая функция
    делят общий хелпер над парой «тип + ключевой параметр» — вторая
    реализация подписи «Группы (4)» не заводится.
- `lib/labels.ts` — там же `schemaErrorCount(issues: SchemaIssue[]): number`
  (только `SEVERITY_ERROR`, spec FR-5/AC-4): предупреждения и info в списке
  не показываются.

### Server components vs client

| Слой | Где | Почему |
| --- | --- | --- |
| `page.tsx` | server | cookie + gRPC (`getActiveTournament`) |

### State

- server-state (номинации, этапы+диагностика) → TanStack Query:
  `useNominations` + `useNominationSchemas` (`useQueries`), мутации —
  существующие хуки с инвалидацией среза `nomination-management`;
- UI-state (открытые модалки, поля форм, id удаляемой номинации) →
  `useState` внутри экрана и модалок (кросс-компонентного шаринга нет,
  Zustand не нужен, ADR 0006);
- сводка схемы, счётчик ошибок, счётчики шапки, номера позиций и доступность
  кнопок приёма — **чистые функции**, не состояние.

## Риски и открытые вопросы

- **N запросов этапов.** Осознанный размен (spec NFR-2): номинаций на
  турнире единицы. В отличие от 0027, периодического обновления нет —
  пачка уходит один раз на открытие экрана и инвалидируется мутациями.
  Агрегирующая ручка остаётся отклонённой альтернативой, а не забытой.
- **Побочный эффект чтения — материализация авто-этапа** (`ListStages`,
  0017, FR-4). Идемпотентен и происходит при любом открытии экрана этапов,
  но теперь случается для **всех** номинаций сразу при открытии списка.
  Ничего не ломает (авто-этап и так подразумевается), однако это первый
  случай, когда экран-список вызывает пишущий по сути RPC — фиксируем
  явно (spec NFR-3), чтобы при будущей чистке «почему у пустой номинации
  есть этап» ответ был записан.
- **Удаление остаётся разрушительным.** Подтверждение с вводом названия —
  UI-защита, а не гейт: сервер по-прежнему удалит номинацию с сыгранными
  боями, а данные модулей `application`/`stage`/`bout` останутся сиротами.
  Формулировка последствий в диалоге пишется **с точки зрения пользователя**
  («будут потеряны заявки, схема, составы и результаты») — это правда для
  него, даже если строки физически остаются в БД. Доменное решение —
  отдельной спекой (spec «Вне скоупа»).
- **Перевод отказа по статусу, а не по тексту.** Если сервер когда-нибудь
  начнёт отдавать 409 на переоткрытие по другой причине, формулировка
  окажется слишком конкретной. Это дешевле и устойчивее сравнения строк;
  альтернатива (типизированный код ошибки в контракте) потребовала бы
  `/proto` и противоречит NFR-1.
- **Гонка «закрыли приём, пока рисовали строку».** Арбитр — сервер; экран
  честно показывает отказ. Предварительно прятать действия по чужому
  состоянию не будем — это создало бы вторую, расходящуюся с сервером,
  копию правила (то же решение, что в 0027).
- **Тост «Отменить» у закрытия приёма честен, только пока переоткрытие
  разрешено сервером.** Сразу после ручного закрытия без распределённых
  бойцов — разрешено (0012, FR-4/AC-16), поэтому обещание выполнимо; если
  «Отменить» всё же получит отказ, показывается тот же тост-ошибка FR-14.
  Фиксируем здесь, чтобы правило не унаследовали вслепую в 0029+.
