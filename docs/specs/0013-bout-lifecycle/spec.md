# Spec: Жизненный цикл боя и текущий бой на арене

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: draft
- Дата: 2026-07-20

## Проблема

Домен боёв разворачивается маленькими инкрементами вдоль турнирного дня.
Уже есть: пары бойцов внутри пула с готовым порядком проведения (0010) и
постановка готового пула на арену целиком — «готовится к запуску» (0011).
Следующий шаг реального турнира — **вести бои**: секретарь на арене открывает
пул, проводит его бои по одному, вводит счёт и фиксирует результат.

Сегодня бой — это только факт «эти двое встретятся» (0010): у него нет ни
состояния (начат/идёт/завершён), ни счёта, ни результата. Пул на арене
«готовится к запуску», но начать его бои негде: у арены на её админ-странице
(0011, FR-9) стоит явный плейсхолдер «ход боя — будущий инкремент». Нужно
**дать бою жизненный цикл и счёт**, а арене — **экран ведения текущего боя**,
чтобы секретарь мог провести пул от первого боя до последнего.

Результат боя — чувствительные данные: по нему считаются места, вокруг него
возникают спорные ситуации («кто выставил этот счёт», «когда бой был
завершён», «почему переоткрыли»). Поэтому бой — **event-sourced агрегат**
(ADR 0011, как заявка 0005): источник истины — неизменяемый журнал доменных
фактов (начат / введён счёт / завершён / переоткрыт / сброшен), а текущее
состояние боя — свёртка этого журнала. Это ровно тот случай, ради которого
ADR 0011 и вводился: нужна история переходов, а не только последнее значение.

Пул на арене ведётся **по одному бою за раз** — это «текущий бой» пула, он же
**текущий бой арены** (пул на арене — один, 0011). Секретарь **циркулирует по
пулу**: переключает, какой бой сейчас текущий, а завершение боя автоматически
подводит текущий указатель к следующему непроведённому.

Всё, что относится к **табло** (таймер, живой счётчик уколов, трансляция
счёта зрителям), в этот инкремент **не входит** — здесь только доменная модель
боя (состояние + итоговый счёт) и её ведение секретарём на арене.

## Акторы

- **admin (секретарь арены)** — на **экране ведения боёв конкретной арены**
  проводит бои стоящего на ней пула: назначает текущий бой (циркуляция по
  пулу), начинает бой, вводит счёт, завершает бой (победитель выводится из
  счёта), при ошибке переоткрывает завершённый или сбрасывает начатый.
  Роль `ROLE_ADMIN` (секретарь = admin, как 0007–0012).
- **боец / гость** — публичного отображения хода боёв, счёта и результатов в
  этом инкременте **нет** (это часть «табло», вне скоупа). На публичном экране
  номинации (0011, FR-11) бои по-прежнему видны как пары + порядок, без
  состояния/счёта. Появление публичных результатов — будущий инкремент вместе
  с табло.

## Домен

### Жизненный цикл боя (event-sourced)

Состояние отдельного боя:

```
не начат  ⇄  идёт  ⇄  завершён
(not_started) (in_progress) (finished)
```

- **не начат (not_started)** — бой сформирован (0010), но не проводился; счёт
  0:0.
- **идёт (in_progress)** — бой начат; секретарь вводит и правит счёт.
- **завершён (finished)** — бой проведён; счёт зафиксирован, из него выведен
  исход (победа A / победа B / ничья).

Переходы (каждый — доменный факт в журнале боя, ADR 0011):

- **Начать** (`не начат → идёт`).
- **Ввести счёт** — изменение счёта бойца A и/или B; допустимо, только пока
  бой `идёт`. Секретарь меняет счёт **быстрыми шагами** (кнопки `+1/−1`,
  `+2/−2`, `+3/−3`, `+5/−5` у каждого бойца) **или задаёт значение вручную**
  (см. «Счёт и исход»). Счёт не опускается ниже 0.
- **Завершить** (`идёт → завершён`) — фиксирует итоговый счёт; исход выводится.
- **Переоткрыть** (`завершён → идёт`) — вернуть завершённый бой в ход, чтобы
  исправить счёт (обратимость, решение №3).
- **Сбросить** (`идёт → не начат`) — вернуть начатый бой в исходное состояние;
  счёт обнуляется (в проекции; журнал хранит прошлое).

Все переходы **обратимы** — секретарь может исправить любую ошибку без потери
истории: каждое действие добавляет **новый** факт в журнал, прошлые факты не
переписываются (ADR 0011).

### Счёт и исход

- У боя два числовых счёта: **очки бойца A** и **очки бойца B**
  (неотрицательные целые, по умолчанию 0:0).
- **Ввод счёта — два способа** (UX, решение №7):
  - **быстрые шаги** — у каждого бойца кнопки `+1/−1`, `+2/−2`, `+3/−3`,
    `+5/−5` (типичные величины уколов/размены в HEMA), меняющие его счёт на
    соответствующую дельту;
  - **ручной ввод** — задать точное значение счёта бойца напрямую.
  - Оба способа приводят счёт к одной и той же паре чисел (A:B); ниже 0 счёт
    не опускается (шаг `−N`, уводящий в минус, ограничивается нулём).
- **Исход выводится из счёта** (не задаётся отдельно): больше очков —
  победа этого бойца; равные очки — **ничья**. Отдельного выбора победителя
  секретарём нет (решение №1).
- Исход осмыслен для завершённого боя; у `не начат`/`идёт` он предварительный.

### Текущий бой пула и арены

- У пула, стоящего на арене, есть **ровно один текущий бой** — тот, что
  секретарь сейчас ведёт. Так как на арене стоит один пул (0011, FR-6),
  **текущий бой пула = текущий бой арены**.
- **Все действия ведения** (начать / ввести счёт / завершить / переоткрыть /
  сбросить) выполняются над **текущим боем**. Чтобы подействовать на другой
  бой пула, секретарь сначала делает его текущим (циркуляция).
- **Циркуляция по пулу**: секретарь может назначить текущим **любой** бой пула
  (в т.ч. уже завершённый — чтобы переоткрыть/поправить). Список боёв пула —
  в порядке проведения (0010, FR-3a/FR-3b).
- **Авто-продвижение**: по умолчанию текущий — **первый непроведённый** бой по
  порядку. Завершение текущего боя автоматически переводит текущий указатель
  на следующий непроведённый бой (решение №2). Ручное назначение (циркуляция)
  переопределяет авто-выбор.
- Вести бои можно только у пула **на арене** (в исполнительной фазе). Пул не на
  арене боёв не ведёт.

### Исполнительный статус пула

Наполняется задел из 0011 (`готовится к запуску → идёт → завершён`):

```
готов → готовится к запуску → идёт → завершён
(ready)   (preparing)          (active)  (finished)
```

- **готовится к запуску (preparing)** — пул на арене, ни один бой не начат
  (как в 0011).
- **идёт (active)** — **начат хотя бы один** бой пула, и не все бои завершены.
  Переход авто (при первом старте боя, решение №4).
- **завершён (finished)** — **все** бои пула завершены. Переход авто (решение
  №4). Пул с 0 боёв (< 2 бойцов, 0010, FR-4) остаётся `готовится к запуску`:
  вести нечего, секретарь просто снимает его.
- **Снятие пула с арены** (0011, FR-8) разрешено **в любой** исполнительной
  фазе, включая `идёт`/`завершён`: **результаты боёв сохраняются** (решение
  №4). После снятия пул освобождает арену, но его исполнительный статус и
  результаты сохраняются; повторная постановка на арену продолжает ведение.

### Защита результатов от пересборки раскладки

Расфиксация раскладки (`ready → draft`, 0009) удаляет бои (0010, FR-5).
В 0011 (FR-3) она уже запрещена, пока хотя бы один пул номинации на арене.
Этот инкремент расширяет запрет: расфиксация запрещена и когда **хотя бы один
бой номинации уже начат или проведён** (у него есть результат) — даже если пул
уже снят с арены (снятие результаты сохраняет). Пересобрать состав можно
только пока боёв с результатами нет (решение №5).

## Пользовательские сценарии

1. Как **секретарь**, я открываю экран ведения боёв арены, на которой стоит
   пул, и вижу его **текущий бой** (пара бойцов) — первый непроведённый по
   порядку.
2. Как **секретарь**, я **начинаю** текущий бой, ввожу по ходу **счёт** обоих
   бойцов — быстрыми кнопками `±1/±2/±3/±5` или вручную — и **завершаю** бой;
   система показывает исход (победа/ничья) из счёта.
3. Как **секретарь**, завершив бой, я вижу, что текущим **автоматически** стал
   следующий непроведённый бой пула — можно вести дальше без ручного выбора.
4. Как **секретарь**, я **циркулирую по пулу** — переключаю текущий бой на
   нужный (в т.ч. назад, на завершённый), чтобы проверить или исправить.
5. Как **секретарь**, я ошибся в счёте завершённого боя — **переоткрываю** его,
   правлю счёт, снова завершаю; история правок сохраняется.
6. Как **секретарь**, я начал бой по ошибке — **сбрасываю** его в «не начат».
7. Как **секретарь/наблюдатель**, я вижу, что пул на арене, где начали бои,
   помечен как **«идёт»**, а когда все бои проведены — **«завершён»**.
8. Как **секретарь**, я **снимаю** с арены пул, бои которого уже проведены
   (например, чтобы освободить площадку), — результаты боёв при этом
   сохраняются.
9. Как **admin**, я **не могу** вернуть раскладку номинации в `draft`, если
   какие-то её бои уже проведены, — система бережёт результаты.

## Требования

Функциональные:

- FR-1: **Бой имеет жизненный цикл** `не начат → идёт → завершён` со всеми
  **обратимыми** переходами (начать, ввести счёт, завершить, переоткрыть,
  сбросить). Каждый переход — новый доменный факт в неизменяемом журнале боя
  (event-sourced, ADR 0011).
- FR-2: **Счёт боя** — два неотрицательных целых (очки бойца A и бойца B),
  по умолчанию 0:0. Ввод/правка счёта допустимы, только пока бой `идёт`.
- FR-2a: **Способы ввода счёта** (UX): у каждого бойца доступны **быстрые
  шаги** `±1`, `±2`, `±3`, `±5` (изменение счёта на дельту) **и ручной ввод**
  точного значения. Счёт каждого бойца не может стать отрицательным: шаг `−N`,
  уводящий ниже 0, ограничивается нулём.
- FR-3: **Исход выводится из счёта**: больше очков — победа бойца, равные —
  ничья. Отдельного выбора победителя нет.
- FR-4: **Начать бой** переводит `не начат → идёт`. Допустимо только над
  текущим боём пула, стоящего на арене.
- FR-5: **Завершить бой** переводит `идёт → завершён`, фиксируя итоговый счёт.
- FR-6: **Переоткрыть** переводит `завершён → идёт` (правка результата);
  **сбросить** переводит `идёт → не начат` (счёт обнуляется).
- FR-7: **Текущий бой.** У пула на арене — ровно один текущий бой; он же
  текущий бой арены (на арене один пул, 0011). Все действия ведения (FR-4..6,
  ввод счёта) выполняются над текущим боём.
- FR-8: **Циркуляция.** Секретарь назначает текущим любой бой пула (включая
  завершённый). Список боёв — в порядке проведения (0010).
- FR-9: **Авто-выбор и авто-продвижение текущего боя.** По умолчанию текущий —
  первый непроведённый бой по порядку; завершение текущего боя переводит
  текущий указатель на следующий непроведённый. Ручное назначение (FR-8)
  переопределяет.
- FR-10: **Исполнительный статус пула** (задел 0011): `готовится к запуску →
  идёт → завершён`. `идёт` — начат ≥1 бой и не все завершены; `завершён` — все
  бои завершены. Переходы **автоматические**. Пул с 0 боёв остаётся `готовится
  к запуску`.
- FR-11: **Снятие пула с арены** (0011, FR-8) разрешено в любой
  исполнительной фазе (`готовится/идёт/завершён`); **результаты боёв
  сохраняются**; исполнительный статус пула сохраняется; арена освобождается.
- FR-12: **Ведение — только на арене.** Начать/вести бой можно только у пула,
  стоящего на арене. У пула не на арене действий ведения нет.
- FR-13: **Защита результатов.** Расфиксация раскладки (`ready → draft`, 0009)
  запрещена, если хотя бы один пул номинации на арене (0011, FR-3) **или** хотя
  бы один бой номинации уже начат/проведён (has result). Иначе — как 0009/0010.
- FR-14: **Экран ведения боёв — на странице арены.** На админ-странице арены
  (0011, FR-9) плейсхолдер «ход боя» заменяется секцией ведения текущего боя
  стоящего пула: пара бойцов, счёт, кнопки начать/завершить/переоткрыть/
  сбросить, переключение текущего боя (циркуляция) по списку боёв пула.
- FR-15: **Права.** Все действия ведения — только `ROLE_ADMIN`. Публичного
  чтения хода/счёта/результатов в этом инкременте нет (см. «Вне скоупа»).

Нефункциональные:

- NFR-1: **История боя — источник истины** (журнал событий, ADR 0011):
  восстановление состояния боя — свёртка журнала; кто и когда начал/ввёл
  счёт/завершил/переоткрыл видно из журнала (задел под разбор споров).
- NFR-2: **Оптимистичная конкуренция по версии потока боя** (ADR 0011, п.3):
  параллельные команды над одним боём сериализуются; конфликт версии → ошибка
  конкуренции (один прозрачный повтор, затем `Aborted`).
- NFR-3: **Инлайн-проекция боя** (ADR 0011, п.4): текущее состояние/счёт боя
  и производные (текущий бой пула, исполнительный статус пула) читаются дёшево,
  без свёртки журнала на каждый список; проекция обновляется атомарно с
  событием.
- NFR-4: Действия ведения — синхронные, без фоновой очереди/табло.
- NFR-5: Модель расширяема под будущее табло (таймер, живой счёт, публичная
  трансляция) и под многотуровость пула без ломки записанной истории боёв.

## Критерии приёмки

- **AC-1** (начать → идёт)
  - Given: пул P на арене R; текущий бой B (не начат, A vs C)
  - When: секретарь начинает B
  - Then: B `идёт`, счёт 0:0; пул P → `идёт`; арена R показывает B текущим
- **AC-2** (счёт и завершение, победитель из счёта)
  - Given: бой B `идёт`
  - When: секретарь вводит счёт 5:3 и завершает B
  - Then: B `завершён`, счёт 5:3, исход — победа бойца A
- **AC-3** (ничья)
  - Given: бой B `идёт`, счёт 4:4
  - When: секретарь завершает B
  - Then: B `завершён`, исход — ничья
- **AC-2a** (быстрые шаги счёта и ограничение нулём)
  - Given: бой B `идёт`, счёт 0:0
  - When: секретарь жмёт бойцу A `+5`, затем `+2`, затем `−3`; бойцу B `+1`,
    затем `−2`
  - Then: счёт 4:0 (A: 5+2−3=4; B: 1−2 ограничено 0)
- **AC-2b** (ручной ввод счёта)
  - Given: бой B `идёт`
  - When: секретарь вводит вручную счёт бойца A = 7, бойца B = 4
  - Then: счёт 7:4
- **AC-4** (счёт только в ходе боя)
  - Given: бой B `не начат` **или** `завершён`
  - When: секретарь пытается ввести счёт, не переоткрыв/не начав
  - Then: операция отклонена (`FailedPrecondition`); счёт не изменился
- **AC-5** (авто-продвижение текущего боя)
  - Given: пул P на арене, бои B1, B2, B3 по порядку; текущий — B1
  - When: секретарь завершает B1
  - Then: текущим автоматически становится B2 (первый непроведённый)
- **AC-6** (циркуляция — ручной выбор)
  - Given: пул P на арене, текущий — B2
  - When: секретарь назначает текущим B1 (завершённый)
  - Then: текущий — B1; доступно переоткрытие/просмотр B1
- **AC-7** (переоткрыть и поправить)
  - Given: бой B `завершён` со счётом 5:3
  - When: секретарь переоткрывает B, ставит 5:5, снова завершает
  - Then: B `завершён`, счёт 5:5, исход — ничья; журнал содержит оба завершения
- **AC-8** (сбросить начатый)
  - Given: бой B `идёт`, счёт 2:1
  - When: секретарь сбрасывает B
  - Then: B `не начат`, счёт 0:0
- **AC-9** (пул → идёт при первом старте)
  - Given: пул P `готовится к запуску` (на арене, ни один бой не начат)
  - When: секретарь начинает первый бой
  - Then: пул P → `идёт`
- **AC-10** (пул → завершён, когда все бои завершены)
  - Given: пул P `идёт`, остался один непроведённый бой
  - When: секретарь завершает последний бой
  - Then: пул P → `завершён`
- **AC-11** (снятие пула с результатами сохраняет их)
  - Given: пул P на арене R, часть боёв проведена (`идёт` или `завершён`)
  - When: admin снимает P с R
  - Then: R свободна; результаты боёв P сохранены; повторная постановка P на
    арену продолжает ведение с сохранёнными результатами
- **AC-12** (нельзя расфиксировать при наличии результатов)
  - Given: раскладка номинации `ready`; пул снят с арены, но у боя есть
    результат (проведён)
  - When: admin пытается вернуть раскладку в `draft`
  - Then: операция отклонена (`FailedPrecondition`): есть проведённые бои
- **AC-13** (ведение только на арене)
  - Given: пул P `готов`, не на арене
  - When: секретарь пытается начать бой пула P
  - Then: операция отклонена (`FailedPrecondition`): пул не на арене
- **AC-14** (права)
  - Given: обычный пользователь или гость
  - When: пытается начать/ввести счёт/завершить бой или сменить текущий
  - Then: операция отклонена (`Unauthenticated` / `PermissionDenied`)
- **AC-15** (конкуренция по версии боя, ADR 0011)
  - Given: два параллельных завершения одного боя из одной версии потока
  - When: обе команды пытаются записать событие
  - Then: применяется одна; вторая после прозрачного повтора при неустранимом
    конфликте отдаёт `Aborted` (состояние не задвоено)

## Вне скоупа

- **Табло**: таймер боя, живой (пошаговый) счётчик уколов, публичная
  трансляция счёта/результатов зрителям и бойцам — отдельный будущий
  инкремент. Здесь — только доменная модель боя (состояние + итоговый счёт) и
  её ведение секретарём.
- **Публичное отображение хода/счёта/результатов боёв** (на экране номинации
  0011 или отдельном) — часть «табло», отложено. Публичный экран 0011
  продолжает показывать бои как пары + порядок, без состояния/счёта.
- **Подсчёт мест/рейтинга по результатам пула** (турнирная таблица, выход из
  группы) — будущий инкремент; здесь бой лишь получает исход, агрегация
  результатов не делается.
- **Судьи/карточки/штрафы/предупреждения, экшены внутри боя** (уколы по зонам,
  обмены) — модель счёта плоская (два числа); детализация — будущее (табло/
  правила).
- **Многотуровость** (пул на нескольких аренах, туры на разных площадках) — как
  0011, один пул ↔ одна арена; модель расширяема (NFR-5).
- **Реакция на снятие/травму бойца во время ведения** (walkover, тех. победа) —
  как 0010/0011, вне скоупа; секретарь при необходимости отражает это счётом
  вручную.
- **Одновременное ведение нескольких боёв одного пула** — пул ведётся по одному
  текущему бою за раз (FR-7).

## Принятые решения

Зафиксировано со стейкхолдером (2026-07-20):

1. **Счёт — два числа, победитель выводится** (FR-2/FR-3): у боя очки бойца A
   и бойца B; больше — победа, равные — ничья. Отдельного выбора победителя нет
   (сохранение простоты; решение судей поверх счёта — вне скоупа).
2. **Текущий бой: авто-продвижение + ручная циркуляция** (FR-8/FR-9): по
   умолчанию текущий — первый непроведённый; завершение продвигает на
   следующий; секретарь может вручную назначить любой бой текущим.
3. **Полная обратимость ЖЦ боя** (FR-1/FR-6): `не начат ⇄ идёт ⇄ завершён` —
   любой переход обратим; исправление ошибок без потери истории, т.к. каждое
   действие — новый факт в журнале (это и есть мотивация event-sourcing,
   ADR 0011).
4. **Авто-переходы статуса пула, снятие активного разрешено** (FR-10/FR-11):
   пул → `идёт` при первом старте боя, → `завершён` когда все бои завершены
   (авто). Снять с арены можно и пул с результатами — результаты сохраняются.
5. **Защита результатов при расфиксации** (FR-13): расфиксацию раскладки
   (`ready → draft`, 0009) блокирует не только пул на арене (0011), но и любой
   уже проведённый бой номинации — чтобы пересборка состава не стёрла
   результаты (0010, FR-5 удаляет бои).
6. **Бой — event-sourced агрегат** (ADR 0011): результат боя — чувствительные
   данные с историей переходов (кто/когда начал/ввёл счёт/завершил/переоткрыл),
   ровно случай ADR 0011. Единица консистентности — отдельный бой (его поток
   событий); текущий бой пула и исполнительный статус пула — производные
   (проекция), не отдельные потоки. Точная архитектурная граница (расширение
   модуля `bout` в event-sourced, направление `pool ↔ bout`, где живёт
   указатель текущего боя) — в `plan.md`.
7. **Ввод счёта — быстрые шаги + ручной ввод** (FR-2a, запрос стейкхолдера
   2026-07-20): у каждого бойца кнопки `±1/±2/±3/±5` (частые величины в HEMA) и
   ручной ввод точного значения; счёт ограничен снизу нулём. Доменно это
   по-прежнему «счёт боя = два неотрицательных целых» (FR-2) — обогащение
   касается способа ввода (UX), а не модели. Как именно команда выражает
   изменение (абсолютная установка A:B vs относительная дельта ±N) — решается в
   `plan.md` с учётом event-sourcing/конкуренции (NFR-2).

## Влияние на 0010/0011

- **0010 (бои внутри пула):** формирование пар и порядок — **без изменений**.
  Модель боя **расширяется** жизненным циклом и счётом; сам модуль боя
  становится **event-sourced** (был CRUD-снапшот). Удаление боёв при
  расфиксации сохраняется, но теперь **гейтится** наличием результатов (FR-13).
- **0011 (пул на арене):** постановка/снятие — сохраняются; **снятие теперь
  разрешено в фазах `идёт`/`завершён`** с сохранением результатов (FR-11).
  Исполнительный статус пула из вычисляемого (`preparing ⟺ arena_id`, 0011)
  становится полноценным `preparing/active/finished` с учётом состояний боёв
  (FR-10) — задел 0011 наполняется. Публичный экран (0011, FR-11) — без
  изменений (результаты не публикуем).

Статус 0010/0011 в индексе `docs/specs/README.md` помечается «изменён 0013».

## События

> Внутримодульный event sourcing боя — по ADR 0011 (принят, применяется в
> `application`): собственный журнал в PG-схеме модуля, инлайн-проекция,
> оптимистичная конкуренция по версии. **Межмодульной** событийной шины
> (публикация событий боя в другие модули) — нет; координация `pool ↔ bout`
> (авто-статус пула, текущий бой, гейт расфиксации) — **синхронная через API
> модуля** (порт, ADR 0002), как `pool → bout`/`pool → arena` в 0010/0011.
> Конкретный механизм (кто читает состояния боёв, где хранится указатель
> текущего боя) — в `plan.md`.

- Издаёт (наружу модуля): нет. Потребляет: нет.
