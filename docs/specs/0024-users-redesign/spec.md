# Spec: Редизайн экрана «Пользователи»

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: done
- Дата: 2026-08-13

## Проблема

Третий инкремент портирования редизайна OpenHEMA (ADR 0015, п.3) и **первый
экранный**: до него были фундамент (0022 — токены и примитивы) и общие
паттерны обратной связи (0023 — скелетоны, тосты, подтверждения, пагинация).
Экран «Пользователи» (`/admin`) выбран первым осознанно: минимум кастомной
логики поверх примитивов, поэтому на нём дёшево закрепить паттерны, которые
повторят двенадцать следующих экранных спек (0025–0036).

Что сегодня не так с самим экраном:

1. **Две карточки вместо одного списка.** «Администраторы» и «Все
   пользователи» — два независимых списка, причём админ виден в обоих
   (второй список — это буквально все учётки). Понять «сколько всего людей в
   системе» по такому экрану нельзя, а одна и та же строка живёт в двух
   местах с разными кнопками.
2. **Нет ни поиска, ни фильтра.** Список отдаётся целиком, найти человека по
   имени или почте можно только глазами. На турнире с сотней заявок это
   перестаёт работать.
3. **Создание админа уведено на отдельную страницу** `/admin/create` плюс
   отдельный пункт навигации `+ Создать админа` — единственный пункт
   верхнего меню, который ведёт не в раздел, а в форму.
4. **Заголовок раздела не соответствует ничему.** Страница называет себя
   «Админка», хотя в навигации это «Пользователи», а header-слоты `AppShell`
   (крошка/заголовок/счётчик/действие), заведённые спекой 0022 «на вырост»,
   до сих пор пусты — 0022 явно оставил их заполнение спекам `0024+`.
5. **Обратная связь на смену роли отсутствует.** Повышение/понижение молча
   перерисовывает список; ошибка сервера («нельзя понизить последнего
   админа») показывается `Alert`-полосой внизу карточки, вне поля зрения
   того, кто только что нажал кнопку в строке.

Отдельно инкремент решает **сквозную задачу**, которая иначе была бы решена
задним числом и по-разному на каждом экране: как экран заполняет header-слоты
общей шапки, если шапку рендерит layout, а данные для неё (счётчики,
действия) знает страница. Ответ, принятый здесь, становится правилом для
0025+.

## Акторы

- **admin** (организатор) — единственный актор экрана: смотрит список
  учётных записей, ищет человека, повышает/понижает роль, заводит нового
  админа.
- **user** и **гость** — на экран не попадают: раздел `/admin/**` закрыт
  серверным guard'ом (ADR 0007), не-админ видит оформленную 403, гость
  отправляется на вход (спека 0023, FR-3). Здесь это поведение не меняется.

## Пользовательские сценарии

1. Как **admin**, я хочу видеть **один список всех учётных записей** с ролью
   и датой регистрации, чтобы понимать состав системы, а не сверять две
   пересекающиеся карточки.
2. Как **admin**, я хочу **отфильтровать список по роли** одним нажатием и
   сразу видеть, сколько в системе админов и сколько обычных пользователей.
3. Как **admin**, я хочу **найти человека по имени или email**, чтобы не
   листать сотню строк ради одной.
4. Как **admin**, я хочу **повысить пользователя до админа или понизить
   админа** прямо из строки и получить подтверждение, что действие
   применилось, — с возможностью тут же его отменить, если ошибся строкой.
5. Как **admin**, я хочу **видеть в своей строке, почему у неё нет кнопки**
   («вы · нельзя понизить себя»), а не пустое место без объяснения.
6. Как **admin**, я хочу **завести нового админа не уходя со списка** —
   формой поверх экрана, после которой он сразу появляется в списке.
7. Как **admin**, я хочу **понятные состояния экрана**: пока список
   грузится — очертания будущей таблицы, а не «Загрузка…»; когда поиск
   ничего не нашёл — сообщение об этом, а не пустая полоса.

## Требования

### Список

- FR-1: Экран показывает **единый список всех учётных записей** (и админов, и
  обычных пользователей) — вместо двух карточек «Администраторы» / «Все
  пользователи». Колонки: **Пользователь** (инициалы, имя, email), **Роль**,
  **Регистрация**, **Действие**.
- FR-2: Колонка **«Регистрация»** показывает дату создания учётной записи в
  относительном виде («сегодня», «вчера», «3 дня назад», далее — дата), с
  полной датой и временем в подсказке при наведении. *(Макет на этом месте
  показывает «Последний вход» — такого факта система не хранит вовсе, ни в
  контракте, ни в данных; заводить его — отдельная фича с изменением API, а
  ADR 0015 фиксирует для этого экрана «новый API не нужен». Колонка
  заменяется на существующий факт, а не имитируется.)*
- FR-3: Порядок строк **детерминирован и не зависит от порядка ответа
  сервера**: сначала админы, затем обычные пользователи; внутри группы — по
  имени, при пустом имени — по email. Так визуальная группировка макета
  (админы сверху) сохраняется без отдельного запроса за админами.
- FR-4: Строка показывает **инициалы** (первые буквы имени; при пустом имени
  — первая буква email) как замену аватара — фотографий система не хранит.

### Фильтр и поиск

- FR-5: Над таблицей — три **взаимоисключающих фильтра по роли**: «Все»,
  «Администраторы», «Пользователи». Активен ровно один; по умолчанию — «Все».
- FR-6: Фильтры «Администраторы» и «Пользователи» показывают **счётчик**
  учётных записей соответствующей роли. Счётчики считаются **по всему
  списку** и не зависят от строки поиска: они отвечают на вопрос «сколько в
  системе», а не «сколько нашлось» (иначе при активном поиске чип
  «Администраторы 0» читался бы как «в системе нет админов»).
- FR-7: **Поиск** по имени и email: подстрока, без учёта регистра, применяется
  вместе с выбранным фильтром роли (логическое И).
- FR-8: Смена фильтра или строки поиска **возвращает список на первую
  страницу** — иначе после сужения выборки можно остаться на несуществующей
  странице и увидеть пустой экран.

### Действия над ролью

- FR-9: В строке обычного пользователя — действие **«Повысить»**, в строке
  админа — **«Понизить»**.
- FR-10: Строка **текущего пользователя** действия не содержит и объясняет
  почему: «вы · нельзя понизить себя».
- FR-11: Успешное повышение/понижение показывает **тост с возможностью
  отмены**: отмена вызывает обратное действие над тем же человеком. Это
  прямое применение правила 0023 («тост — успех и отменяемое действие») к
  операции, которая обратима одним обратным вызовом. Отмена, в свою очередь,
  сообщает об успехе **без** новой кнопки отмены — чтобы пара действий не
  зациклилась.
- FR-12: Отказ сервера (нельзя понизить себя, нельзя понизить последнего
  оставшегося админа — ADR 0007) показывается **тостом-ошибкой с текстом
  сервера**, без кнопки «Повторить»: отказ детерминированный, повтор даст тот
  же результат. Список при этом остаётся в прежнем состоянии.
- FR-13: Подтверждающая модалка на смену роли **не показывается** — правило
  0023 отводит модалку только необратимым действиям, а смена роли обратима
  (и опасные случаи всё равно отклоняет сервер).

### Создание админа

- FR-14: Новый админ заводится **в модальном окне поверх списка**, которое
  открывается действием «+ Создать админа» в шапке раздела. Поля — имя,
  email, пароль; в окне — пояснение, что ролей всего две и здесь сразу
  заводится ADMIN, а повышение/понижение обычных пользователей делается
  кнопками в списке.
- FR-15: Незаполненные/некорректные поля показываются **инлайн у поля**
  (правило 0023), ошибка сервера (например, email занят) — **внутри
  модалки**, которая остаётся открытой с введёнными данными, а не тостом
  поверх закрывшегося окна.
- FR-16: Успешное создание закрывает модалку, показывает тост об успехе и
  **обновляет список** — новый админ виден сразу, без перезагрузки страницы.
- FR-17: Отдельная страница `/admin/create` и пункт верхнего меню
  «+ Создать админа» **удаляются**: после FR-14 это второй вход в ту же
  форму, а пункт меню — единственный в навигации, ведущий не в раздел.
  *(Осознанное следствие: сохранённые ссылки на `/admin/create` перестают
  работать.)*

### Шапка раздела

- FR-18: Экран заполняет **шапку раздела**: крошка «ПОЛЬЗОВАТЕЛИ · <название
  турнира>» (без турнира — только «ПОЛЬЗОВАТЕЛИ»), заголовок «Пользователи»,
  счётчик «N учётных записей», действие «+ Создать админа».
- FR-19: Способ, которым экран заполняет шапку, — **общий механизм, а не
  разовое решение**: строка заголовка раздела отделяется от общей шапки
  приложения и рендерится самим экраном. Правило фиксируется в `web/AGENTS.md`
  и действует для спек 0025+.

### Состояния экрана

- FR-20: Пока список грузится — **скелетон в форме будущей таблицы** (0023),
  не спиннер и не текст «Загрузка…».
- FR-21: Ошибка загрузки списка показывается **на месте таблицы** с
  возможностью повторить запрос.
- FR-22: Пустые состояния **различаются по причине**: «в системе нет ни одной
  учётной записи» и «по фильтру/поиску ничего не найдено» — разные тексты,
  второй подсказывает сбросить поиск.
- FR-23: Список **разбит на страницы** клиентской навигацией (0023) с
  фиксированным размером страницы.

### Нефункциональные

- NFR-1: Инкремент — **чисто клиентский**: ни одного изменения в `/proto` и
  на сервере (ADR 0015 фиксирует для этого экрана «новый API не нужен»).
- NFR-2: Фильтрация, поиск и постраничная навигация выполняются **на уже
  загруженном списке**. Серверный поиск/постраничность потребовали бы
  изменения контракта и потому вне скоупа. **Известный предел**: экран
  рассчитан на сотни учётных записей (масштаб турнира), при десятках тысяч
  деградирует — осознанный размен, зафиксированный здесь, а не обнаруженный
  потом.
- NFR-3: Экран работает в обеих темах и собран из примитивов 0022/0023 —
  новых визуальных решений «мимо» дизайн-системы не вводится.
- NFR-4: Управляющие элементы остаются настоящими элементами управления:
  действия — кнопки, фильтры — переключатели с состоянием «выбран», поиск —
  поле с доступным именем. Клавиатурная навигация и кольцо фокуса (0023) не
  теряются при переходе на табличную вёрстку.

## Критерии приёмки

- **AC-1 (единый список)**
  - Given: в системе 3 админа и 5 обычных пользователей
  - When: admin открывает `/admin`
  - Then: он видит одну таблицу из 8 строк; каждая учётка встречается ровно
    один раз; админы идут выше обычных пользователей

- **AC-2 (колонка регистрации)**
  - Given: учётная запись создана вчера
  - When: admin смотрит её строку
  - Then: в колонке «Регистрация» — «вчера», а в подсказке — полная дата и
    время

- **AC-3 (счётчики фильтров)**
  - Given: в системе 3 админа и 164 пользователя
  - When: admin открывает экран и вводит в поиск строку, под которую
    подходит один пользователь
  - Then: счётчики фильтров остаются «Администраторы 3» и «Пользователи 164»,
    а в таблице — одна строка

- **AC-4 (фильтр по роли)**
  - Given: открыт список всех учёток
  - When: admin нажимает «Администраторы»
  - Then: в таблице остаются только админы, фильтр помечен как выбранный,
    остальные два — нет

- **AC-5 (поиск)**
  - Given: в системе есть «Анна Кораблёва» (`a.korableva@klinok.ru`)
  - When: admin вводит «КОРАБ» (в другом регистре)
  - Then: строка находится; поиск по части email даёт тот же результат

- **AC-6 (фильтр + поиск вместе)**
  - Given: выбран фильтр «Пользователи»
  - When: admin вводит строку, под которую подходит и админ, и обычный
    пользователь
  - Then: в таблице остаётся только обычный пользователь

- **AC-7 (повышение с отменой)**
  - Given: строка обычного пользователя
  - When: admin нажимает «Повысить» и операция удалась
  - Then: показан тост «повышен до ADMIN» с действием «Отменить»; строка
    получила роль ADMIN; нажатие «Отменить» вызывает понижение того же
    человека и сообщает об успехе уже без кнопки отмены

- **AC-8 (своя строка)**
  - Given: admin смотрит список
  - When: он находит собственную строку
  - Then: кнопки действия там нет, вместо неё — «вы · нельзя понизить себя»

- **AC-9 (отказ сервера)**
  - Given: в системе остался один админ, и он же — текущий пользователь
  - When: сервер отклоняет понижение (последний админ)
  - Then: показан тост-ошибка с текстом сервера и без кнопки «Повторить»;
    роль в списке не изменилась

- **AC-10 (создание админа)**
  - Given: открыт список
  - When: admin нажимает «+ Создать админа» в шапке, заполняет имя/email/
    пароль и подтверждает
  - Then: модалка закрывается, показан тост об успехе, новый админ появляется
    в таблице без перезагрузки страницы

- **AC-11 (ошибка создания)**
  - Given: открыта модалка создания, email уже занят
  - When: admin подтверждает создание и сервер отвечает ошибкой
  - Then: модалка остаётся открытой с введёнными данными, ошибка показана
    внутри неё

- **AC-12 (страница создания удалена)**
  - Given: приложение собрано после инкремента
  - When: смотрим пункты верхнего меню админки и роуты
  - Then: пункта «+ Создать админа» в меню нет, страницы `/admin/create` нет,
    единственный вход в форму — действие в шапке

- **AC-13 (шапка раздела)**
  - Given: активный турнир называется «Клинок Севера 2026», в системе 167
    учёток
  - When: admin открывает `/admin`
  - Then: в шапке — крошка «ПОЛЬЗОВАТЕЛИ · КЛИНОК СЕВЕРА 2026», заголовок
    «Пользователи», счётчик «167 учётных записей» и действие «+ Создать
    админа»; при отсутствии активного турнира крошка — «ПОЛЬЗОВАТЕЛИ»

- **AC-14 (состояния)**
  - Given: список ещё грузится
  - When: экран отрисован
  - Then: видны скелетон-строки в форме таблицы, без текста «Загрузка…»;
    при ошибке загрузки — сообщение с возможностью повторить; при пустом
    результате поиска — текст «ничего не найдено», отличный от текста «нет
    ни одной учётной записи»

- **AC-15 (пагинация)**
  - Given: учёток больше, чем помещается на страницу
  - When: admin переходит на вторую страницу и затем меняет фильтр
  - Then: список возвращается на первую страницу выбранной выборки

## Вне скоупа

- **«Последний вход»** — факт не хранится; заведение его (поле в контракте,
  запись при входе) — отдельная фича с изменением API, вне границы ADR 0015
  для этого экрана.
- **Серверный поиск и постраничность** — потребовали бы изменения `/proto`
  (см. NFR-2).
- **Сортировка по колонкам, массовые действия, экспорт списка** — макет их
  не предполагает.
- **Редактирование профиля пользователя и удаление учётных записей** — таких
  операций в системе нет вовсе.
- **Приглашения по email, сброс пароля** — отсутствующий API, зарезервировано
  за 0037/0038 (ADR 0015).
- **Редизайн остальных экранов** — каждый своей спекой (0025–0036).

## [NEEDS CLARIFICATION]

Открытых вопросов нет — четыре развилки закрыты решением пользователя
(2026-08-13):

1. Колонка «Последний вход» → **заменяется на «Регистрация»** (существующая
   дата создания), API не расширяем (FR-2).
2. Создание админа → **только модалка**; роут `/admin/create` и пункт
   навигации удаляются (FR-14, FR-17).
3. Механизм header-слотов → **отдельный компонент заголовка раздела**,
   который рендерит сама страница; общая шапка остаётся только верхней
   полосой (FR-19).
4. Обратная связь на смену роли → **тост с отменой**, вызывающей обратное
   действие (FR-11).
