# Spec: Кодген контрактов без внешнего реестра плагинов

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: ready
- Дата: 2026-09-17

## Проблема

Деплой препрода на ВМ (`make deploy`, спека 0048) больше не проходит: первый
же шаг — генерация кода из контрактов — падает.

Диагностика 2026-09-17 (воспроизведено прямо на препрод-ВМ):

```
$ make generate
cd server && go tool buf generate ../proto --template ../proto/buf.gen.yaml
Failure: permission_denied: 403 Forbidden
make: *** [Makefile:39: generate] Error 1
```

Причина: генерация настроена на **удалённое исполнение плагинов** — все три
генератора (Go-сообщения, Connect-Go, TypeScript) объявлены в
`proto/buf.gen.yaml` как `remote: buf.build/...`, то есть работу выполняет не
локальная машина, а внешний реестр `buf.build`. С IP препрод-ВМ этот реестр
отдаёт `403 Forbidden` **на любой запрос**, включая корневую страницу
(`curl https://buf.build/` → `403 Forbidden`) — это блокировка по адресу, а
не проблема авторизации или токена.

Что важно для оценки масштаба (тоже проверено на ВМ):

- **Заблокирован только `buf.build`.** `proxy.golang.org` → 200,
  `registry.npmjs.org` → 200, Docker Hub → 401 (т.е. достижим), GitHub → 200.
- **Сам инструмент работает.** `make lint-proto` (`buf lint`) проходит, и
  `make sqlc` проходит (35 с) — они в реестр не ходят. Деплой блокирует ровно
  один шаг из всей цепочки.
- **Обойти нечем.** Сгенерированный код в репозитории не хранится (ADR 0004),
  а образы `server`/`web` собираются из контекста хоста — значит результат
  генерации обязан физически существовать на ВМ до сборки. На ВМ сейчас лежит
  копия, сгенерированная до блокировки; она устарела — контракты менялись
  2026-09-17 (спека 0049), и выкатить это изменение на препрод невозможно.

Отдельно: зависимость от внешнего реестра **не даёт проекту ничего**, чего
нельзя получить иначе — версии генераторов в `buf.gen.yaml` даже не
зафиксированы (плагины берутся «последние»), то есть сегодня результат
генерации у разных людей и в CI воспроизводим лишь по случайности.

## Акторы

- **admin (deployer)** — разворачивает и обновляет препрод на ВМ; запускает
  `make deploy`, который начинается с кодгена. Сегодня заблокирован полностью.
- **разработчик** — после `git clone`/`git pull` выполняет `make generate` и
  `make sqlc` (раздел «Онбординг» корневого `AGENTS.md`). Сегодня работает,
  но только пока внешний реестр доступен с его адреса.
- **CI** (GitHub Actions) — генерирует код перед сборкой, тестами и линтом.
  Сегодня работает (раннеры GitHub не заблокированы).

## Пользовательские сценарии

1. Как **admin**, я хочу развернуть на препроде текущую версию проекта, чтобы
   изменения контрактов доезжали до препрода, а не застревали на шаге
   генерации.
2. Как **admin**, я хочу, чтобы деплой не зависел от доступности стороннего
   сервиса, к которому у меня нет и не может быть доступа, — чтобы выкатка не
   ломалась заново по причинам вне моего контроля.
3. Как **разработчик**, я хочу генерировать код после `git pull` теми же
   командами, что и раньше, не заводя учётных записей и не настраивая обходов
   доступа.
4. Как **разработчик**, я хочу, чтобы версии генераторов были зафиксированы в
   репозитории наравне с остальными зависимостями, чтобы у всех участников и в
   CI получался один и тот же результат.
5. Как **разработчик**, я хочу, чтобы случайный возврат к внешнему реестру
   (например, копипастом из чужого примера) ловился автоматически, а не
   всплывал через месяц очередным сломанным деплоем.

## Требования

- FR-1: Генерация кода из контрактов выполняется **без обращений к внешнему
  реестру плагинов**: на машине, где `buf.build` недоступен, шаг генерации
  проходит успешно.
- FR-2: Результат генерации функционально эквивалентен нынешнему — сервер и
  клиент собираются, существующие тесты проходят **без правок прикладного
  кода**. Смена способа генерации не является изменением API.
- FR-3: Версии всех генераторов зафиксированы в репозитории как обычные
  зависимости и согласованы с версиями runtime-библиотек, которыми
  пользуется сгенерированный код.
- FR-4: `make deploy` на препрод-ВМ проходит шаг кодгена целиком, без ручных
  обходов (без копирования результата с машины разработчика, без VPN/прокси).
- FR-5: Возврат к удалённому исполнению плагинов ловится автоматической
  проверкой (тест/CI), а не внимательностью ревьюера.
- FR-6: Команды онбординга и деплоя остаются прежними (`make generate`,
  `make sqlc`, `make deploy`). Если для их работы требуется новое окружение —
  это отражено в документации онбординга и в процедуре разворачивания.
- FR-7: Кодген **не требует установки генераторов и их тулчейнов на хост**:
  на машине, где есть Docker (он и так нужен стеку), генерация проходит без
  локальной установки генераторов и сред их исполнения.
- FR-8: Версии генераторов не дублируются: окружение, в котором они
  исполняются, собирается из версий, **уже зафиксированных в манифестах
  репозитория**, а не из отдельного списка версий, живущего рядом и
  расходящегося с ними.
- NFR-1: Время генерации остаётся сопоставимым с нынешним (сейчас ~2 с
  локально); генерация не становится шагом, который заметно удлиняет деплой.
  Разовая подготовка окружения кодгена (первая сборка) под это не подпадает —
  она кешируется и повторяется только при смене версий.
- NFR-2: Существующие проверки контрактов (`buf lint`, `buf breaking` в CI)
  продолжают работать без изменения смысла.
- NFR-3: Правило «сгенерированный код не хранится в репозитории» (ADR 0004)
  остаётся в силе — фича меняет способ генерации, а не место хранения.

## Критерии приёмки

- **AC-1** (главный — снятие блокера)
  - Given: препрод-ВМ, с которой `buf.build` отдаёт `403 Forbidden`
  - When: admin выполняет на ней `make codegen` (генерация из контрактов + sql)
  - Then: шаг завершается успешно, в рабочей копии появляется актуальный
    сгенерированный код, соответствующий текущим контрактам

- **AC-2** (деплой целиком)
  - Given: та же ВМ, актуальный `main` с изменившимися контрактами (0049)
  - When: admin выполняет `make deploy`
  - Then: деплой доходит до запуска стека; шаг генерации не является причиной
    остановки

- **AC-3** (эквивалентность результата)
  - Given: рабочая копия до изменения способа генерации и после
  - When: выполнена генерация обоими способами и результаты сравнены
  - Then: сгенерированный код совпадает либо расходится только несущественно
    (версия генератора в шапке); `go build ./...`, `go vet ./...`,
    `pnpm exec tsc --noEmit`, `pnpm build` и `make test-all` — зелёные, при
    этом прикладной код не правился

- **AC-4** (нет обращений к реестру)
  - Given: любая машина с доступом к контрактам
  - When: выполняется генерация
  - Then: ни один шаг генерации не обращается к `buf.build`; конфигурация
    генерации не содержит удалённо исполняемых плагинов

- **AC-5** (защита от регресса)
  - Given: кто-то вернул в конфигурацию генерации удалённо исполняемый плагин
  - When: прогоняются тесты/CI
  - Then: проверка падает с понятным сообщением, объясняющим, почему так
    нельзя (ссылка на эту спеку/ADR)

- **AC-6** (фиксация версий)
  - Given: чистый клон репозитория на другой машине
  - When: выполняется генерация
  - Then: используются версии генераторов, зафиксированные в репозитории, — а
    не «последние доступные на момент запуска»

- **AC-7** (ничего не ставим на хост, FR-7)
  - Given: машина, на которой не установлено ни одного генератора и ни одной
    среды их исполнения — есть только Docker и рабочая копия репозитория
  - When: выполняется генерация
  - Then: она проходит успешно и не требует установки чего-либо на хост

- **AC-9** (версии не дублируются, FR-8)
  - Given: в манифесте репозитория поднята версия runtime-библиотеки, парной
    к генератору
  - When: окружение кодгена пересобрано и генерация выполнена заново
  - Then: сработал генератор ровно этой версии; отдельного места, где версию
    нужно править вручную второй раз, не существует

- **AC-8** (онбординг не сломан)
  - Given: разработчик с чистым клоном, следующий разделу «Онбординг»
    корневого `AGENTS.md`
  - When: он выполняет описанные там команды
  - Then: получает рабочую сборку; все дополнительные требования к окружению
    перечислены в документации заранее

## Вне скоупа

- **Перенос сборки образов в CI и выкатка готовых образов из registry**
  (обсуждалось как альтернатива: ВМ только `docker compose pull`). Решает ту
  же проблему шире и попутно снимает медленную сборку на 2 CPU, но это
  отдельная и более крупная перестройка деплоя — не смешиваем.
- **Доставка сгенерированного кода с машины разработчика на ВМ** (rsync/архив)
  — рассмотрено и отклонено: ВМ перестаёт быть самодостаточной, появляется
  риск рассинхрона «контракты ↔ сгенерированный код».
- **Хранение сгенерированного кода в git** — отмена ADR 0004 не обсуждается.
- **Обход блокировки на ВМ** (VPN/прокси/зеркало реестра) — лечит симптом,
  оставляет зависимость от чужой доступности.
- **Замена `sqlc`/`goose`** — они не затронуты, на ВМ работают и в
  заблокированный реестр не ходят; остаются как есть (хостовый `go tool`).
  Перенос и их в контейнер — возможное продолжение, но к этой проблеме
  отношения не имеет.
- **Изменение самих контрактов** — фича не меняет ни одного `.proto`.
