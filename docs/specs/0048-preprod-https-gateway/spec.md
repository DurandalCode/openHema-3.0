# Spec: HTTPS-шлюз для preprod (TLS перед веб-слоем)

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: ready
- Дата: 2026-09-13

## Проблема

Сегодня стек (`docker-compose.yml`, `make prod`) обслуживает трафик по
обычному HTTP: BFF (`web`) и Go-сервер (`server`) публикуют свои порты
напрямую на хост, без TLS. Для выхода в препродакшен сайт должен стать
доступен из интернета на реальном домене по HTTPS с валидным (доверенным
браузером) сертификатом — иначе гейт публичного доступа (спека 0046) и вся
остальная публичная часть открываются анонимам по незащищённому каналу, а
браузеры показывают предупреждение о небезопасном соединении.

Отдельная сложность: домен для preprod ещё не был настроен на момент
написания этой спеки (будет привязан к серверу в процессе того же
разворачивания, для которого пишется эта спека) — то есть результатом фичи
должна быть не только работающая конфигурация, но и понятная
последовательность действий «указали домен → получили рабочий HTTPS» для
человека, разворачивающего препрод.

## Акторы

- **admin (deployer)** — разворачивает и обслуживает preprod: настраивает
  DNS домена на сервер, поднимает стек, получает валидный сертификат;
  впоследствии сертификат обновляется автоматически без его ручного участия.
- **guest / user** (посетитель браузера) — попадает на сайт только по
  HTTPS; обращение по обычному `http://` не должно приводить к показу
  незащищённого содержимого.
- **внешний мониторинг/health-check** — не является актором HTTPS-гейта
  специально, но не должен пострадать от изменений (см. NFR-2 спеки 0046).

## Пользовательские сценарии

1. Как **admin**, я хочу, указав домен на IP сервера и один раз развернув
   стек, получить рабочий HTTPS без ручной возни с сертификатами, чтобы
   препрод можно было поднять по понятной процедуре, а не методом проб.
2. Как **admin**, я хочу, чтобы сертификат обновлялся сам по себе до
   истечения срока действия, чтобы сайт не «падал» по TLS без моего участия.
3. Как **guest**, зайдя по старой привычке на `http://<домен>`, я хочу
   оказаться на защищённой версии сайта, а не увидеть отдельную
   незащищённую копию или ошибку.
4. Как **admin**, я хочу, чтобы внутренний Go-сервер (gRPC/Connect) не был
   напрямую доступен из интернета — наружу должна смотреть только точка
   входа HTTPS, а внутренний сервис остаётся доступен только BFF, как и
   предполагает текущая архитектура (ADR 0001: BFF — единственный сетевой
   клиент сервера).
5. Как **разработчик**, проверяющий фичу локально через уже существующий
   способ (`docker compose up --build`, п. Definition of Done в
   `AGENTS.md`), я хочу, чтобы это по-прежнему работало без домена и
   сертификата, чтобы изменения этой фичи не сломали существующий процесс
   локальной докеризованной проверки.

## Требования

- FR-1: Внешний трафик к preprod-стеку обслуживается по HTTPS с
  сертификатом, которому браузер доверяет без предупреждений (валидный
  сертификат для реального домена, а не самоподписанный).
- FR-2: Запрос по обычному HTTP (порт 80) к домену preprod перенаправляется
  на HTTPS-версию того же адреса (включая путь и параметры запроса), а не
  отдаёт содержимое напрямую.
- FR-3: Внутренний Go-сервер (gRPC/Connect) не должен быть напрямую
  достижим из интернета — единственная публично открытая точка входа
  обслуживает HTTPS и проксирует на BFF; связь BFF→сервер остаётся
  внутренней (согласуется с ADR 0001).
- FR-4: Выпуск и продление TLS-сертификата автоматизированы как часть
  стека — при штатной эксплуатации admin не выполняет ручных действий по
  продлению до истечения срока действия сертификата.
- FR-5: Процедура разворачивания даёт admin понятную последовательность
  действий для первого запуска на новом домене: что настроить на стороне
  DNS (домен указывает на сервер) и что запустить на сервере, чтобы после
  этого сайт заработал по HTTPS.
- FR-6: Существующий health-check (см. NFR-2 спеки 0046) остаётся доступен
  по тем же правилам, что и сегодня — эта фича не меняет его исключение из
  гейта препрода и не завязывает его доступность на наличие домена/TLS.
- FR-7: Фича ограничена топологией «один хост, весь стек через
  `docker-compose`» — сценарий с внешним управляемым балансировщиком/CDN,
  который уже терминирует TLS до наших контейнеров, не рассматривается (см.
  «Вне скоупа»).
- FR-8: Существующий локальный докеризованный прогон стека без домена
  (`docker compose up --build`, используется для проверки модулей перед
  мержем — см. Definition of Done в корневом `AGENTS.md`) продолжает
  работать по обычному HTTP, без необходимости покупать домен/сертификат
  для одной лишь локальной проверки.

### Нефункциональные

- NFR-1: Добавление HTTPS не требует изменений в коде server/web —
  конфигурация только на уровне деплоя/инфраструктуры (в духе гейта
  препрода, спека 0046, — там режимы тоже переключаются конфигурацией).
- NFR-2: Секреты/приватные ключи TLS не попадают в git — только плейсхолдер
  в `.env.example` (правило 6 корневого `AGENTS.md`).
- NFR-3: Перезапуск/передеплой стека не приводит к повторному запросу
  сертификата с нуля (сертификат переживает рестарт контейнеров) — чтобы не
  упереться в лимиты запросов удостоверяющего центра.

## Критерии приёмки

- **AC-1**
  - Given: DNS домена указывает на IP сервера, стек развёрнут
  - When: посетитель открывает `https://<домен>`
  - Then: сайт открывается с сертификатом, которому браузер доверяет без
    предупреждений
- **AC-2**
  - Given: стек развёрнут и обслуживает домен по HTTPS
  - When: посетитель открывает `http://<домен>/некоторый/путь?x=1`
  - Then: браузер перенаправляется на `https://<домен>/некоторый/путь?x=1`
- **AC-3**
  - Given: стек развёрнут
  - When: кто-либо снаружи хоста пытается подключиться напрямую к порту
    внутреннего gRPC/Connect-сервера
  - Then: подключение недоступно — порт не опубликован наружу
- **AC-4**
  - Given: срок действия сертификата приближается к истечению
  - When: наступает момент планового продления
  - Then: сертификат продлевается автоматически, без ручных действий
    admin и без простоя сайта
- **AC-5**
  - Given: новый сервер, домен ещё не настроен
  - When: admin выполняет документированные шаги разворачивания (указать
    DNS, запустить стек с указанием домена)
  - Then: по завершении сайт работает по HTTPS «из коробки», без
    дополнительных незадокументированных действий
- **AC-6**
  - Given: локальная докеризованная проверка (`docker compose up --build`)
    без указанного домена
  - When: разработчик обращается к сайту как и раньше (по HTTP/локальному
    адресу)
  - Then: поведение не отличается от сегодняшнего — фича не требует домена
    для этого сценария
- **AC-7**
  - Given: health-check эндпоинт (спека 0046, NFR-2)
  - When: внешний мониторинг обращается к нему как и раньше
  - Then: ответ не меняется и не зависит от состояния HTTPS/домена

## Вне скоупа

- Сценарий с внешним управляемым балансировщиком/CDN, который сам
  терминирует TLS до наших контейнеров (см. FR-7) — не рассматривается;
  пользователь подтвердил топологию «один VPS, docker-compose».
- Автоматизация покупки домена или управления DNS-записями у
  регистратора — admin настраивает A-запись домена вручную на стороне
  регистратора/DNS-провайдера; фича начинается с того, что домен уже указан
  на сервер.
- Web Application Firewall, защита от DDoS и продвинутое кэширование на
  уровне шлюза сверх штатного поведения выбранного в `plan.md` решения.
- Wildcard- и мультидоменные сертификаты — один домен для одного
  preprod-окружения.
- Изменение логики самого гейта препрода/паузы регистрации (спека 0046) —
  эта фича добавляет только транспортный уровень (HTTPS), не трогая правила
  видимости страниц.
- HTTP/3 и прочие продвинутые возможности прокси сверх необходимого для
  FR-1..FR-4.
