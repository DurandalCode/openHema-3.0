## Обзор решения

Фича — целиком инфраструктурная (docker-compose), без изменений в коде
server/web (NFR-1 спеки). Перед `web` в стек добавляется реверс-прокси,
который терминирует TLS и автоматически получает/продлевает сертификат
Let's Encrypt для публичного домена. Порты `server`/`web` перестают
публиковаться в базовом `docker-compose.yml` (FR-3) — но чтобы не сломать
существующий локальный докеризованный прогон (`make prod`, `make dev`,
FR-8/AC-6), их публикация возвращается через `docker-compose.override.yml`,
который Compose подключает автоматически при обычном `docker compose up`.

Компоуз-профиль для публичного запуска называется **`prod`**, а не
`preprod` — топология «прокси + скрытые внутренние порты» одна и та же что
для препрода, что для будущего боевого прод-запуска (это не разные фичи,
второй раз строить то же самое незачем); отдельного профиля/файла под
«настоящий прод» заводить не нужно, пока не появится реальная причина им
разойтись (решение пользователя 2026-09-13). Название существующего
Makefile-таргета `prod` при этом не трогаем — он уже занят под локальный
докер-прогон для проверки (Definition of Done, корневой `AGENTS.md`), и
путать эти два смысла нельзя. Новый таргет, запускающий компоуз-профиль
`prod`, называется `make deploy`.

### Выбор технологии прокси: Caddy, не nginx

Пользователь в постановке задачи сам был не уверен насчёт nginx — решаем
здесь. Берём **Caddy**, а не nginx+certbot:

- Caddy получает и продлевает сертификат Let's Encrypt **сам**, без
  отдельного контейнера certbot, cron-задачи продления и сигнала
  reload — закрывает FR-4/NFR-3 одной строкой конфига (домен в адресе
  блока), а не отдельным подсистемным compose-сервисом.
- HTTP→HTTPS редирект (FR-2) для доменных (не `localhost`/IP) адресов —
  поведение по умолчанию, не требует отдельной директивы.
- Меньше движущихся частей = меньше шагов в процедуре разворачивания
  (FR-5) и меньше того, что может разъехаться между nginx.conf и
  certbot-контейнером.

nginx+certbot остаётся стандартной альтернативой (вода не режется —
работает так же), но добавляет минимум ещё один сервис и ручную связку
reload по обновлению сертификата; сознательно не выбран ради простоты
процедуры для admin.

## Контракты (proto)

Не применимо — фича не меняет доменные контракты `/proto`.

## Server (модули и слои)

Не применимо — код `server` не меняется (NFR-1). `server` продолжает
слушать `:8080` внутри compose-сети; после этой фичи порт просто не
публикуется наружу при `make deploy` (см. «Инфраструктура»).

## Web (FSD + BFF)

Не применимо — код `web` не меняется (NFR-1). Вся публичная поверхность
(гейт — спека 0046) продолжает обслуживаться `web`; после этой фичи трафик
до `web` приходит либо напрямую (локальный докер-прогон через override),
либо через прокси (`make deploy`).

**Уточнение по ходу реализации** (найдено при проверке T2, до этого в плане
ошибочно значился несуществующий `app/api/health/route.ts` — спека 0000
статуса «пример», в коде не реализована): реальный health-check — это
`/healthz` на самом `server` (`server/internal/platform/platform.go`,
незащищённый хендлер на общем mux, порт 8080), а не на `web`. Внешний
мониторинг сегодня стучится в `server:8080/healthz` напрямую, пользуясь тем,
что порт `server` сейчас публикуется в хост. После FR-3 (порт `server`
больше не публикуется) это перестало бы работать — правки в разделе
«Инфраструктура» ниже добавляют в Caddyfile отдельный маршрут `/healthz` →
`server:8080` (остальное — в `web:3000`), чтобы FR-6/AC-7 выполнялись без
изменений в коде `server`.

## Инфраструктура (docker-compose)

- **`docker-compose.yml` (база)**:
  - Убрать `ports:` у `server` (сейчас `8080:8080`) и у `web` (сейчас
    `${WEB_PORT:-3000}:3000`) — по умолчанию (без override) ничего не
    публикуется напрямую, только через прокси (FR-3).
  - Новый сервис `proxy` (образ `caddy:2-alpine`), профиль
    `prod` (`profiles: ["prod"]`) — не поднимается обычным
    `docker compose up` без `--profile prod`, чтобы не требовать
    свободных 80/443 и домен при локальном прогоне (FR-8/AC-6).
    - `ports: ["80:80", "443:443"]`
    - `volumes:`
      - `./deploy/Caddyfile:/etc/caddy/Caddyfile:ro`
      - именованный том `caddy_data:/data` (сертификаты и состояние ACME
        переживают рестарт/передеплой — NFR-3)
      - именованный том `caddy_config:/config`
    - `environment: PUBLIC_DOMAIN`, `ACME_EMAIL` (проброс из `.env`)
    - `depends_on: web, server`
  - Новые именованные тома: `caddy_data`, `caddy_config`.
- **`docker-compose.override.yml` (новый файл, только для локального
  докер-прогона)**:
  - Возвращает `server`: `ports: ["8080:8080"]`.
  - Возвращает `web`: `ports: ["${WEB_PORT:-3000}:3000"]`.
  - Compose подключает этот файл автоматически при обычном
    `docker compose up` (без `-f`) — то есть `make dev` (поднимает только
    `postgres`, не затронут) и `make prod` (`docker compose up --build`)
    продолжают работать буквально как сегодня: те же порты, без прокси
    (профиль `prod` не активирован без явного `--profile`), без домена
    (AC-6). Имя Makefile-таргета `prod` и имя compose-профиля `prod` не
    связаны — таргет `make prod` компоуз-профиль вообще не указывает.
- **`deploy/Caddyfile`** (новый файл):
  ```
  {
      email {$ACME_EMAIL}
  }

  {$PUBLIC_DOMAIN} {
      handle /healthz {
          reverse_proxy server:8080
      }
      handle {
          reverse_proxy web:3000
      }
  }
  ```
  Один домен на блок (мультидомен/wildcard — вне скоупа). Автоматическая
  выдача/продление сертификата и HTTP→HTTPS редирект — поведение Caddy по
  умолчанию для доменных адресов (FR-1, FR-2, FR-4, AC-1, AC-2, AC-4).
  `/healthz` — отдельный маршрут на `server:8080` (реальный health-check,
  см. уточнение в разделе «Web» выше и FR-6/AC-7); весь остальной путь —
  на `web:3000`. Наружу через прокси открыт только этот один путь `server`,
  остальной RPC-поверхности `server` снаружи по-прежнему нет (FR-3).
- **`Makefile`**: новый таргет `deploy` (имя `prod` уже занято локальным
  докер-прогоном — см. «Обзор решения»):
  ```makefile
  .PHONY: deploy
  deploy: ## Публичный запуск: TLS-прокси + весь стек без прямых портов (требует PUBLIC_DOMAIN, ACME_EMAIL в .env)
  	$(MAKE) codegen
  	docker compose -f docker-compose.yml --profile prod up -d --build
  ```
  Явный `-f docker-compose.yml` исключает `docker-compose.override.yml` —
  порты `server`/`web` не публикуются, а `--profile prod` включает
  `proxy`. `make prod` не меняется — остаётся сегодняшним локальным
  докер-прогоном (override подключается автоматически, профиль не
  активирован, `docker compose up` без `--profile` его не включает).
- **`.env.example`**: добавить секцию под новые переменные:
  ```
  # ── HTTPS-шлюз для публичного запуска (спека 0048, make deploy) ──
  # Домен, на который указывает DNS этого сервера. Обязателен для
  # `make deploy` — без него сервис proxy не сможет получить сертификат.
  PUBLIC_DOMAIN=
  # Контактный email для уведомлений удостоверяющего центра (Let's
  # Encrypt) об истечении сертификата. Опционален.
  ACME_EMAIL=
  ```
- **Процедура для admin (FR-5)** — фиксируется в `README.md`/`AGENTS.md`
  рядом с существующим «Быстрый старт» (задача T5 в `tasks.md`):
  1. Указать A-запись домена на IP сервера (вручную у DNS-провайдера —
     вне скоупа автоматизации, см. «Вне скоупа» спеки).
  2. Заполнить `PUBLIC_DOMAIN`, `ACME_EMAIL` в `.env` на сервере.
  3. `make deploy`.
  4. Дождаться, пока Caddy получит сертификат (первый запрос до готовности
     ACME может занять до ~минуты) — сайт становится доступен по
     `https://<домен>`.

## Тестирование

> Фича инфраструктурная — юнит/e2e-пирамида ADR 0003 здесь неприменима
> буквально (нет доменной логики в коде). Проверка — конфигурационная и
> смоук на реальном докере/домене.

- `docker compose -f docker-compose.yml -f docker-compose.override.yml
  config` и `docker compose -f docker-compose.yml --profile prod config`
  — оба варианта валидны (нет ошибок YAML/интерполяции).
- Локальный смоук без домена: `make prod` — стек поднимается, `web`/`server`
  отвечают на прежних портах как до фичи (AC-6), `proxy` не поднят.
- Смоук `make deploy` на реальном сервере с настроенным `PUBLIC_DOMAIN`:
  - `https://<домен>` открывается без предупреждения браузера (AC-1).
  - `http://<домен>/...` редиректит на `https://<домен>/...` (AC-2).
  - Порт 8080 (и 3000) не отвечают на внешний хост (AC-3).
  - `https://<домен>/healthz` отвечает `ok` как раньше (AC-7).
- Автопродление (AC-4) не проверяется живым ожиданием срока действия
  сертификата в рамках этой фичи — полагаемся на встроенный механизм Caddy
  (стандартное, документированное поведение), риск отмечен ниже.

## Риски и открытые вопросы

- Если `PUBLIC_DOMAIN` не указан, а admin всё равно запустит `make
  deploy` — таргет уже проверяет это сам и останавливается с понятным
  сообщением до запуска compose (реализовано в T4, не «при необходимости»).
- **Найдено и исправлено при проверке (T7/T8)**: `${ACME_EMAIL:-}` пустой
  строкой ломал старт Caddy — Caddyfile-директиве `email` нужен ровно один
  аргумент, а пустая строка внутри `{$ACME_EMAIL}` даёт синтаксическую
  ошибку парсинга (плейсхолдер-дефолт самого Caddy `{$VAR:default}` для
  этого не срабатывает — он смотрит только на unset, не на заданную пустую
  строку). Исправлено подстановкой дефолта на уровне compose-интерполяции:
  `ACME_EMAIL: ${ACME_EMAIL:-admin@${PUBLIC_DOMAIN:-example.invalid}}` в
  `docker-compose.yml` (compose-`:-` реагирует и на unset, и на пустую
  строку). Проверено локально: `--profile prod` с `PUBLIC_DOMAIN=localhost`
  без `ACME_EMAIL` — `proxy` поднимается и обслуживает `/` (200, → `web`) и
  `/healthz` (200 `ok`, → `server`) по HTTPS (самоподписанный сертификат
  Caddy для `localhost`), `http://` редиректит на `https://` (308), порты
  8080/3000 на хосте не отвечают.
- Первый запуск `make deploy` на новом домене требует, чтобы порты 80/443
  сервера были реально открыты наружу (файрвол/security group) — вне
  контроля этой фичи, фиксируется в процедуре (FR-5) как предварительное
  условие.
- Смена `PUBLIC_DOMAIN` на другой домен потребует повторной выдачи
  сертификата (Caddy справится сам), но старые данные ACME в томе
  `caddy_data` для прежнего домена останутся — не мешает работе, но можно
  почистить том вручную при полной смене домена.
