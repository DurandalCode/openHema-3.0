# Spec: Дизайн-система — токены и базовые UI-примитивы

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.
> Первый инкремент портирования редизайна OpenHEMA — см. `docs/adr/0015-ui-redesign-porting-order.md`
> за полным порядком и границами последующих инкрементов.

- Статус: ready
- Дата: 2026-08-12

## Проблема

UI приложения складывался по мере фич без сквозной визуальной системы:
цвета/радиусы/типографика частично зафиксированы (спека 0004 — палитра
зелёный+золото), но нет единого набора переиспользуемых интерактивных
паттернов (кнопки, бейджи, теги, поля, чипы фильтров, табы, карточки, пустые
состояния, модалки, таблицы, шапка приложения) — каждый экран стилизуется
заново поверх минимального набора shadcn-компонентов.

В `claude.ai/design` (проект «OpenHEMA») подготовлен полный визуальный
редизайн: единая палитра/типографика/радиусы/высоты + 14 переиспользуемых
компонентов, уже покрывающих большинство экранов приложения в обеих темах.
Перенос этой системы в `web/src` — фундамент, от которого зависят все
последующие спеки редизайна конкретных экранов (порядок — ADR 0015): без
готовых примитивов каждая экранная спека была бы вынуждена придумывать
стилизацию заново.

## Акторы

- **user** / **admin** — видят единый визуальный язык (цвета, типографика,
  состояния кнопок/полей/бейджей, отступы) на всех экранах платформы вместо
  разрозненной стилизации; тёмная/светлая тема продолжает работать как
  сейчас.
- **разработчик/агент следующих спек** — прямой потребитель: использует
  готовый набор примитивов `shared/ui` вместо вёрстки с нуля на каждом
  экране редизайна.

## Пользовательские сценарии

1. Как **user/admin**, я хочу видеть единый визуальный язык на всех экранах
   платформы (согласованные цвета, типографика, отступы, состояния
   интерактивных элементов), чтобы интерфейс не выглядел как набор
   разрозненных заплаток.
2. Как **user/admin**, я хочу переключать тёмную/светлую тему как сейчас, и
   чтобы обновлённые компоненты корректно и без визуальных дефектов
   поддерживали обе темы.
3. Как **разработчик следующей спеки редизайна** (напр. «Пользователи»,
   «Заявки»), я хочу найти в `shared/ui` готовый набор примитивов новой
   дизайн-системы (кнопки, бейджи, теги, поля, чипы фильтров, табы, карточки,
   пустые состояния, модалки, заголовок/строка таблицы, шапка приложения),
   чтобы не дублировать вёрстку и не изобретать стилизацию заново на каждом
   экране.

## Требования

- FR-1: Палитра, типографика, радиусы и высоты контролов новой дизайн-системы
  полностью заменяют текущие (палитра зелёный+золото спеки 0004 — в части
  цвета — считается заменённой), выражены как CSS-переменные, управляемые
  существующим механизмом темы (`next-themes`, класс `.dark` на `<html>`) —
  без второго, параллельного механизма переключения темы (никакого
  прокидывания пропа `theme` по дереву компонентов, как в исходном дизайне).
- FR-2: Следующие примитивы доступны в `shared/ui` с визуалом, отвечающим
  дизайн-системе, и с сохранённой либо улучшенной реальной интерактивностью
  (не декоративный мок): кнопка, бейдж, тег, поле ввода (текст/выбор/поиск —
  контролируемый компонент с реальным вводом), чип фильтра (с состоянием и
  счётчиком), табы, карточка, пустое состояние, модальное окно (с доступностью
  — управление фокусом, закрытие по Escape, ARIA-разметка), заголовок таблицы,
  строка таблицы. Компоненты с прямым текущим аналогом обновляются на месте
  (те же файлы получают новые варианты/токены, не дублируются параллельным
  набором); тег, чип фильтра, заголовок и строка таблицы — новые файлы в том
  же `shared/ui` (аналогов сейчас нет).
- FR-3: Шапка приложения (для админ-экранов) — единый компонент с корректным
  списком пунктов навигации, соответствующим реальным разделам приложения
  (без пунктов, ведущих в никуда), поддерживающим обе темы через тот же
  единый механизм, без раздельных копий компонента на тему.
- FR-4: Все существующие места использования текущих переиспользуемых
  UI-компонентов (навигация, диалог входа/регистрации и т.п.) продолжают
  работать визуально и функционально корректно после обновления примитивов.
- FR-5: Карточка бойца (`UiFighterCard` в исходном дизайне) в эту фичу не
  входит — переносится вместе со спекой редизайна экрана «Бойцы», так как
  это компонент, специфичный для домена бойцов, а не общий примитив.

Нефункциональные:

- NFR-1: Обе темы (светлая/тёмная) визуально соответствуют дизайн-системе
  без регрессий контраста/читаемости текста и интерактивных элементов.
- NFR-2: Фича не вводит новых серверных/API-контрактов — чисто UI-слой
  (никаких изменений в `/proto` или server-модулях).

## Критерии приёмки

- **AC-1**
  - Given: пользователь на любом экране, использующем обновлённые примитивы
  - When: он переключает тему (светлая/тёмная)
  - Then: все элементы (кнопки, бейджи, поля, карточки, модалки, таблицы,
    шапка) визуально корректно меняются вместе с темой без ручного
    управления темой на уровне отдельного компонента
- **AC-2**
  - Given: форма с текстовым/выборочным/поисковым полем на основе нового
    примитива поля ввода
  - When: пользователь вводит текст или выбирает значение
  - Then: значение реально меняется и передаётся обработчику (не статичный
    декоративный текст)
- **AC-3**
  - Given: открыто модальное окно на основе нового примитива
  - When: пользователь нажимает Escape или кликает вне окна
  - Then: окно закрывается; фокус клавиатуры остаётся внутри окна, пока оно
    открыто
- **AC-4**
  - Given: администратор на любом экране админки
  - When: он смотрит на шапку/навигацию приложения
  - Then: видит только пункты, ведущие на реально существующие разделы
    приложения (без несуществующих ссылок)
- **AC-5**
  - Given: существующие экраны, использующие текущие переиспользуемые
    компоненты (навигация, диалог входа/регистрации)
  - When: примитивы обновлены до новой дизайн-системы
  - Then: эти экраны продолжают работать без визуальных поломок или потери
    функциональности

## Вне скоупа

- Редизайн конкретных экранов (админских и публичных) — отдельные
  последующие спеки по порядку из ADR 0015.
- Карточка бойца (`UiFighterCard`) — переносится со спекой «Бойцы» (FR-5).
- Боковая навигация (`UiSideNav`) как отдельный самостоятельный публичный
  компонент — в реальных экранах не используется (только как альтернатива в
  галерее дизайн-системы), не входит в эту фичу (см. ADR 0015, «Границы»).
- Toast-уведомления, подсказки (tooltip), пагинация, хлебные крошки, поле
  даты/времени, паттерны loading/error/confirm из «Состояния и обратная
  связь» — отдельная последующая спека (не входят в список 14 примитивов
  дизайн-системы).
- `drafts/*` файлы исходного дизайн-проекта — не переносятся.
- Новые серверные возможности — этот инкремент чисто визуальный.
