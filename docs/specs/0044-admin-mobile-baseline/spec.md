# Spec: admin-mobile-baseline

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: ready
- Дата: 2026-08-30

## Проблема

Админ-панель спроектирована и реализована только под десктопный экран.
Базовый каркас (верхняя навигация, строка заголовка раздела, контейнеры
контента) не адаптируется под узкий экран: содержимое не занимает всю
доступную ширину/высоту viewport'а, а навигация с восемью пунктами не
помещается на узком экране. В результате часть разделов админки на
мобильном устройстве физически неудобна или недостижима, даже для простых
действий (посмотреть список, поменять статус) — не говоря уже об экранах,
рассчитанных на активную работу (живой скоринг, пульт турнира).

Решение пользователя (2026-08-30): не ждать полного мобильного дизайна
каждого экрана. Сначала — этой спекой — устранить общие структурные
проблемы каркаса, из-за которых админка на мобильном выглядит и ведёт себя
сломанной. Экраны, для которых важна продуманная мобильная эргономика
(не просто «помещается», а «удобно работать»), получат отдельный дизайн и
будут реализованы отдельной следующей спекой.

Актуальность: организаторы/операторы турнира на площадке часто держат под
рукой только телефон, а не ноутбук.

## Акторы

- **admin** — организатор/оператор турнира, работает в админ-панели, в т.ч.
  с телефона или узкого планшета на площадке турнира.

## Пользовательские сценарии

1. Как **admin**, я хочу открыть любой раздел админки с телефона и увидеть
   контент, который занимает весь экран (а не сжат в узкую колонку с пустыми
   полями), чтобы не тратить экранное пространство впустую.
2. Как **admin**, я хочу добраться до любого раздела навигации с телефона
   (сейчас восемь пунктов верхнего меню не помещаются на узком экране),
   чтобы не быть ограниченным подмножеством разделов, доступных только с
   десктопа.
3. Как **admin**, я хочу, чтобы страница не скроллилась вбок целиком
   из-за одного слишком широкого блока (таблицы, формы), чтобы навигация и
   контент оставались управляемыми одним вертикальным скроллом.
4. Как **admin**, я хочу, чтобы стандартные интерактивные элементы (кнопки,
   пункты меню, поля форм) на мобильном экране были достаточно крупными для
   пальца, а не только для курсора мыши.

## Требования

- FR-1: Каркас админки (верхняя навигация + строка заголовка раздела)
  должен корректно отображаться на узких экранах, без обрезания и наложения
  элементов друг на друга.
- FR-2: Все пункты навигации админки должны оставаться доступными на узком
  экране без десктопного разрешения.
- FR-3: Контентная область экрана должна использовать всю доступную ширину
  viewport'а на узком экране (никаких десктопных фиксированных отступов/
  максимальных ширин, оставляющих пустые поля по бокам).
- FR-4: Ни один экран админ-раздела не должен вызывать горизонтальный
  скролл всей страницы целиком на узком экране.
- FR-5: Интерактивные элементы каркаса и стандартных форм/списков (кнопки,
  пункты меню, поля ввода) должны соответствовать минимальному размеру
  тач-таргета, пригодному для управления пальцем.
- FR-6: На узком экране навигация переключается на полноценное мобильное
  меню (все пункты доступны через явное открытие/закрытие, а не через
  горизонтальный скролл вкладок) — это часть общего фикса каркаса, а не
  временная заглушка.
- FR-7: Экраны с активными операционными данными — живой скоринг арены и
  пульт турнира — на узком экране как минимум помещаются в экран и не
  ломают вёрстку (базовая пригодность); их углублённая мобильная
  эргономика (расположение под работу с телефона в моменте боя/наблюдения)
  — предмет следующей спеки.
- FR-8: Списки/таблицы с большим числом колонок (бойцы, заявки, ростер) на
  узком экране скроллятся по горизонтали в границах своего контейнера, не
  вызывая скролл всей страницы; набор колонок и карточный вид не меняются
  в этой спеке.
- FR-9: Модальные окна создания/редактирования сущностей на узком экране
  раскрываются на весь экран (или как bottom sheet) вместо центрированного
  окна с полями по бокам.

- NFR-1: Baseline гарантированно поддерживает ширину экрана от 360px и
  выше. Более узкие экраны (320px и подобные) не гарантируются.

## Критерии приёмки

- **AC-1**
  - Given: admin открывает любой раздел `/admin/*` на устройстве с узким
    экраном
  - When: страница загрузилась
  - Then: контент занимает всю ширину экрана, навигация видна и доступна
    целиком (без горизонтального скролла всей страницы)
- **AC-2**
  - Given: admin находится в любом разделе `/admin/*` на узком экране
  - When: admin пытается перейти в любой другой раздел из навигации
  - Then: переход возможен без переключения на десктопное разрешение
- **AC-3**
  - Given: экран содержит таблицу/список шире доступной ширины
  - When: admin просматривает экран на узком устройстве
  - Then: вбок скроллится только сама таблица/список в своём контейнере, а
    не страница целиком (навигация и остальной контент остаются на месте)
- **AC-4**
  - Given: admin на узком экране (минимум 360px)
  - When: admin открывает навигацию
  - Then: все пункты навигации доступны через явно открывающееся/
    закрывающееся мобильное меню, ни один пункт не обрезан и не скрыт без
    возможности до него добраться
- **AC-5**
  - Given: admin на узком экране открывает живой скоринг арены или пульт
    турнира
  - When: экран загрузился
  - Then: контент помещается в экран без обрезания и без горизонтального
    скролла всей страницы (тонкая эргономика не гарантируется — только
    базовая пригодность)
- **AC-6**
  - Given: admin на узком экране открывает диалог создания/редактирования
    сущности (например, добавление бойца)
  - When: диалог открылся
  - Then: диалог занимает весь экран (или раскрывается снизу как bottom
    sheet) вместо центрированного окна с пустыми полями по бокам

## Вне скоупа

- Продуманная (не просто «помещается») мобильная эргономика живого
  скоринга арены и пульта турнира — расположение элементов под работу с
  телефона в моменте боя/наблюдения. Эта спека даёт им только базовую
  пригодность (FR-7/AC-5); углублённый дизайн — предмет следующей спеки.
- Изменение набора колонок таблиц/списков или переход на карточный вид на
  мобильном — в этой спеке списки остаются табличными и скроллятся по
  горизонтали (FR-8).
- Другие «важные» экраны, которые пользователь спроектирует отдельно и
  которые не относятся к общему каркасу (конкретный список — предмет
  следующей спеки).
- Нативное мобильное приложение / PWA-специфичные возможности (офлайн,
  push, установка на домашний экран).
- Изменение контента/функциональности экранов — только их пригодность к
  узкому экрану.
- Поддержка экранов уже 320px и подобных «сверхузких» — baseline
  гарантируется от 360px (см. NFR-1).
