# Spec: Доменные пробелы, вскрытые редизайном

> Артефакт SDD (ADR 0008). Описывает **ЧТО и ЗАЧЕМ**. Без технологий, API и
> схем БД — только предметная область. Реализация — в `plan.md`.

- Статус: done
- Дата: 2026-08-25

> Состав, номер и имя фичи зафиксированы заранее в `docs/adr/0017-deferred-
> debt-porting-order.md` (п. 2 порядка) как разбор долга, отложенного
> спеками `0022`–`0038`. Это первая из пяти спек порядка с реальным риском
> целостности данных, поэтому она идёт сразу после `0039`.

## Проблема

Пять экранных спек редизайна (`0026`, `0028`, `0034`/`0037`/`0038` совместно,
`0036`, `0038`) одна за другой упирались в доменные решения, которые не
описывает UI, и откладывали их с формулировкой «доменное изменение, не
редизайн» или «вернуться отдельной спекой». В результате в системе остаются
пять конкретных дыр:

1. Удаление номинации ничем не защищено: сервер удаляет запись без проверки,
   что на неё уже опираются данные других модулей (распределённые бойцы,
   поставленные и завершённые бои) — единственный пункт всего долга ADR 0017
   с риском целостности данных, а не просто недостающей функциональности.
2. Возврат выведенного бойца на турнир необратимо стирает его посев: боец
   всегда попадает обратно в «нераспределённые», даже если стадия ещё не
   ушла вперёд и прежний пул существует.
3. Связь «учётка ↔ боец» открыта ADR 0016 только в одну сторону (боец узнаёт
   себя из кабинета); организатор не может увидеть обратное — какой учётке
   принадлежит боец в ростере, найти бойца по учётке или свести дубли одного
   человека.
4. Заявитель не видит историю событий своей заявки, хотя сервер её уже
   считает и отдаёт (`GetApplication`) — публичный экран показывает только
   текущий статус.
5. У турнира нет структурированной программы по дням («сбор в 9:00, начало
   боёв в 10:00»): в профиле есть только границы события целиком
   (`EventStartAt`/`EventEndAt`), содержательное расписание существует
   только в дизайн-макете.

## Акторы

- **admin** — организатор турнира: удаляет номинации, возвращает выведенных
  бойцов, ищет и сводит связку «учётка ↔ боец» в ростере, ведёт программу
  турнира по дням.
- **user** — заявитель/боец: читает историю событий своей заявки; программу
  турнира по дням видит как гость (см. ниже), отдельного действия не
  совершает.
- **гость** — читает программу турнира по дням на публичной афише/странице
  турнира.

## Пользовательские сценарии

1. Как **admin**, я хочу, чтобы система не дала мне удалить номинацию, если
   в ней уже распределены бойцы или идут/прошли бои, чтобы не оставлять в
   чужих модулях данные, ссылающиеся на несуществующую номинацию.
2. Как **admin**, я хочу, чтобы при возврате бойца на турнир он по
   возможности снова оказался в том пуле, откуда его вывели, чтобы не
   пересобирать посев вручную после каждого возврата.
3. Как **admin**, я хочу видеть в ростере, какой учётке принадлежит боец
   (если она есть), искать бойца по учётке пользователя и сводить дубликаты
   одного и того же человека, чтобы вести список участников, а не
   разрозненные записи.
4. Как **user**, я хочу видеть историю событий своей заявки (кто и когда
   менял статус), а не только текущее значение, чтобы понимать, что с ней
   происходило.
5. Как **гость**, я хочу видеть программу турнира по дням на афише и
   странице турнира, чтобы знать время сбора и порядок мероприятий, не
   уточняя это у организатора.

## Требования

### Гейт на удаление номинации (сценарий 1)

- FR-1: Система должна отказывать в удалении номинации, если выполняется
  хотя бы одно из условий: (а) в номинации есть боец, распределённый в пул
  любой её стадии; (б) в номинации есть хотя бы один поставленный
  (в процессе или завершённый) бой.
- FR-2: Отказ должен быть различим для вызывающего (структурированная
  доменная ошибка, а не общий отказ) — экран `0028` уже показывает
  подтверждение с вводом названия перед вызовом удаления (FR-15 спеки 0028)
  и должен суметь показать причину отказа, а не только факт неудачи.
- FR-3: Номинация без распределённых бойцов и без боёв удаляется как и
  сегодня — без изменений в этом случае.
- FR-3a: Форс-пути (каскад/архивация связанных данных) не заводится.
  Единственный способ удалить заблокированную номинацию — вручную снять
  распределение бойцов и сбросить посев через уже существующие операции
  (`UnassignFighter`/`ResetLayout` и т.п.), пока условие FR-1 не перестанет
  выполняться. Решение пользователя (2026-08-25): согласуется с
  существующим паттерном кода (`WithdrawFighter` вместо физического удаления
  бойца, `DeletePool` блокируется вне `draft`) — необратимое удаление данных
  участников система последовательно избегает.

### Восстановление посева при возврате бойца (сценарий 2)

- FR-4: Система должна запоминать пул, из которого выведен распределённый
  боец, на момент вывода.
- FR-5: При возврате бойца система должна пытаться поместить его обратно в
  запомненный пул, но только пока стадия этого пула ещё в статусе `draft`
  (решение пользователя 2026-08-25: тот же порог, по которому уже
  блокируется `DeletePool` — посев вне `draft` считается зафиксированным,
  и это правило не меняется ради возврата одного бойца).
- FR-6: Восстановление в запомненный пул невозможно, если стадия ушла из
  `draft` к моменту возврата, либо если сам пул к этому моменту удалён. В
  обоих случаях система должна поместить бойца в «нераспределённые» и явно
  сообщить, что автоматическое восстановление не удалось — как и сегодня,
  без силового восстановления любой ценой. **Уточнено интеграционной
  проверкой T31 (2026-08-25):** если стадия уже была вне `draft` в момент
  самого вывода, FR-4 не запоминает ничего (запоминание работает только для
  `draft`-членств) — но и не трогает членство пула, которое для стадий вне
  `draft` не подчищается лениво (тот же порог, что у `DeletePool`). Боец в
  этом случае при возврате естественным образом снова оказывается в том же
  пуле — не через механизм FR-4/FR-5, а потому что членство никогда не
  удалялось; отдельная обработка «в нераспределённые» для этого случая не
  нужна и не реализуется.
- FR-7: Боец, выведенный без распределения (уже был в «нераспределённых»),
  при возврате остаётся в «нераспределённых» — не регрессия.

### Обратная проекция «учётка ↔ боец» в админке (сценарий 3)

- FR-8: Система должна показывать в ростере админки, привязан ли боец к
  учётке пользователя, без раскрытия этого на публичных или пользовательских
  экранах (граница ADR 0016 сохраняется: обратное направление — только для
  организатора).
- FR-9: Admin должен иметь возможность найти бойца по учётке пользователя.
- FR-10: Admin должен иметь возможность свести два дубля одного и того же
  участника (записи бойца одного турнира) в одну запись — полное слияние:
  участия в номинациях и результаты боёв дубля-источника переносятся на
  итоговую запись, дубль-источник помечается объединённым (не удаляется
  физически — тот же принцип, что и остальной домен участников). Решение
  пользователя (2026-08-25).
- FR-10a: Если у обеих записей задан свой `origin_user_id` (обе привязаны к
  разным учёткам), слияние переносит привязку итоговой записи на
  `origin_user_id` той записи, которую admin выбрал целевой; привязка
  записи-источника снимается (partial-unique индекс `(tournament_id,
  origin_user_id)` не допускает двух активных привязок на одну запись).
- FR-11: Правка снапшота бойца через эту проекцию не появляется — она
  остаётся только у существующего админского редактирования (ADR 0016,
  «Что не меняется»).

### История событий заявки для заявителя (сценарий 4)

- FR-12: Заявитель должен видеть хронологию событий своей заявки (кто менял
  статус и когда) — те же данные, что уже видит admin на экране `0025`,
  сервер их уже отдаёт по `GetApplication`.
- FR-13: История доступна заявителю только по своей заявке — правило доступа
  не меняется (уже соблюдается сервером: `Get` возвращает `ErrForbidden` не
  владельцу и не admin).

### Программа турнира по дням (сценарий 5)

- FR-14: Admin должен иметь возможность задать программу турнира — список
  дней, каждый день — упорядоченный список пунктов «время + короткий текст»
  (например «9:00 — сбор», «10:00 — начало номинаций»), по образцу макета
  20a. Решение пользователя (2026-08-25).
- FR-14a: Дни программы задаются admin вручную (свободные даты), без
  жёсткой привязки к `EventStartAt`/`EventEndAt` турнира — многодневный
  турнир может иметь программу по дням независимо от того, заданы ли уже
  границы события целиком.
- FR-15: Программа турнира по дням должна отображаться гостю на публичной
  афише и на странице турнира (`/about`), рядом с уже выведенными местом
  проведения, взносом и регламентом (`0037`, `0039`).
- FR-16: Турнир без заданной программы отображается как сегодня — без
  пустого раздела или заглушки.

### NFR

- NFR-1: Ни один из пяти пунктов не меняет опубликованные ранее отказы по
  домену (ADR 0017, «Контекст»): судья боя, номер заявки, удаление бойца,
  раунды внутри боя, целевой счёт — этой спекой не заводятся.
- NFR-2: Публичность данных не расширяется сверх сценария: обратная
  проекция «учётка ↔ боец» видна только admin (FR-8), связь «учётка → свой
  боец» ADR 0016 не меняется.

## Критерии приёмки

- **AC-1**
  - Given: в номинации есть распределённый в пул боец
  - When: admin пытается удалить номинацию
  - Then: система отказывает, номинация и связанные данные остаются
    нетронутыми
- **AC-2**
  - Given: в номинации есть завершённый бой
  - When: admin пытается удалить номинацию
  - Then: система отказывает
- **AC-3**
  - Given: номинация не имеет ни распределённых бойцов, ни боёв
  - When: admin удаляет номинацию
  - Then: номинация удаляется, как и до этой спеки
- **AC-4**
  - Given: боец распределён в пул A, admin выводит его с турнира
  - When: admin возвращает бойца на турнир (пул A всё ещё существует и
    восстановление возможно)
  - Then: боец снова в пуле A, посев остальных участников пула не изменился
- **AC-5**
  - Given: боец распределён в пул A, admin выводит его с турнира, затем
    стадия пула A переходит из `draft` в следующий статус (или пул A
    удаляется)
  - When: admin возвращает бойца на турнир
  - Then: боец оказывается в «нераспределённых», интерфейс явно показывает,
    что автоматическое восстановление не удалось
- **AC-6**
  - Given: боец турнира, у которого есть привязанная учётка (регистрировался
    через заявку с этой учётки)
  - When: admin открывает карточку бойца в ростере
  - Then: видно, что у бойца есть привязанная учётка
- **AC-7**
  - Given: admin знает учётку пользователя
  - When: admin ищет бойца по этой учётке
  - Then: находится боец, привязанный к этой учётке в активном турнире (если
    есть)
- **AC-8**
  - Given: заявитель подал заявку, admin один раз сменил её статус
  - When: заявитель открывает свою заявку
  - Then: заявитель видит и текущий статус, и запись о смене (кто, когда)
- **AC-9**
  - Given: чужая заявка (не своя и не admin)
  - When: пользователь пытается получить историю чужой заявки
  - Then: доступ отклонён (как и сегодня для самой заявки)
- **AC-10**
  - Given: admin задал программу турнира из нескольких дней с пунктами
    вида «время + текст»
  - When: гость открывает публичную афишу или `/about`
  - Then: гость видит программу по дням с пунктами в заданном порядке
- **AC-11**
  - Given: у турнира не задана программа по дням
  - When: гость открывает публичную афишу или `/about`
  - Then: раздел программы не показывается (как и сегодня)
- **AC-12**
  - Given: два дубля одного участника, у каждого своё участие в разных
    номинациях
  - When: admin сводит дубли, выбрав одну запись целевой
  - Then: итоговая запись показывает участия из обеих исходных записей,
    запись-источник помечена объединённой и больше не фигурирует как
    отдельный активный боец в ростере
- **AC-13**
  - Given: номинация с распределённым бойцом, admin вручную снимает
    распределение и сбрасывает посев этой номинации до пустого состояния
  - When: admin повторно пытается удалить номинацию
  - Then: удаление проходит — условие FR-1 больше не выполняется

## Вне скоупа

- **Отказы по домену из спек 0022–0038** (судья, раунды внутри боя, целевой
  счёт, номер заявки, удаление бойца) — не пересматриваются (ADR 0017,
  «Границы»).
- **Правка снапшота бойца пользователем** — остаётся у организатора
  (ADR 0016 подтверждена, не разворачивается).
- **Прогноз времени боя и очереди, время простоя площадки** — операционная
  модель, отдельный порядок `0043` (ADR 0017, п. 5).
- **Серверный поиск и постраничность для ростера/заявок**, агрегирующая
  выдача живых статусов, экспорт списков — масштаб, спека `0041`.
- **Подтверждение/смена email, персистентность сессий, почтовые
  уведомления, объектное хранилище для файла регламента, общий rate
  limiting по IP** — инфраструктура, спека `0042`.
- **Загрузка файла программы турнира** (PDF) вместо структурированных
  пунктов — тем же решением, что уже принято для регламента (`0037`,
  решение п. 2): ссылка/структурированные поля, не файл.
- **Уведомления о смене статуса заявки** заявителю (почта/пуш) — есть в
  `0042`, здесь заявитель узнаёт историю только при явном просмотре заявки,
  не проактивно.
- **Полностью автоматическое построение программы по дням** из
  `EventStartAt`/`EventEndAt` или из живой ленты боёв — программа остаётся
  анонсом организатора, не расчётом (ADR 0017, «Границы»: «это анонс
  организатора, а не расчёт»).

## [NEEDS CLARIFICATION]

Открытых вопросов нет. Решения приняты пользователем 2026-08-25:

1. Гейт на удаление номинации — только запрет, без форс-пути с каскадом/
   архивацией (FR-3a).
2. Восстановление посева при возврате — попытка только пока стадия в
   `draft` (FR-5/FR-6).
3. Слияние дублей бойца — полное слияние с переносом участий/результатов на
   итоговую запись (FR-10/FR-10a).
4. Программа турнира по дням — день → список пунктов «время + текст»
   (FR-14/FR-14a).

Слияние дублей ограничено записями **одного турнира** (см. акторов и
границы модуля `fighter`, который не хранит участников кросс-турнирно) —
дубли из разных турниров этой спекой не рассматриваются, т.к. `Fighter` —
самостоятельная запись на каждый турнир (0007).
