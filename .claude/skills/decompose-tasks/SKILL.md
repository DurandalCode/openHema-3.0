# Skill: decompose-tasks

Раскладывает уже готовый `tasks.md` на самодостаточные карточки задач
(ADR 0021), чтобы конкретные задачи можно было отдать локальной модели
через opencode-скилл `implement-task`. Не меняет сам `tasks.md` как чеклист
и не имплементирует ничего.

## Предусловие

Есть заполненные `docs/specs/NNN-*/{spec.md,plan.md,tasks.md}`. Если нет —
сначала `write-spec`.

## Шаги

1. **Выбрать задачи.** Пройти невыполненные (`- [ ]`) пункты `tasks.md`
   сверху вниз.
2. **Классифицировать каждую.**
   - `requires: local` — типовая пара тест→код на известном слое, которая
     зеркалит существующий паттерн в кодовой базе (напр. auth-модуль как
     референс для нового модуля, соседний RPC-хендлер как референс для
     нового). Слабой модели достаточно примера + точного описания, чтобы
     повторить паттерн.
   - `requires: claude` — новый server-модуль/bounded context "с нуля" без
     прямого референса, изменение `proto`-контрактов, миграции со
     структурными решениями (см. ADR 0008 про DDL целиком), что угодно,
     что может потребовать нового ADR или доменного решения не из плана.
     Для таких задач карточка **не создаётся** — они остаются обычными
     пунктами `tasks.md`, их доделывает `tdd-cycle`.
3. **Собрать контекст для `local`-задач.** Для каждой: найти референсную
   реализацию (модуль/файл, который явно или неявно предлагается
   зеркалить), прочитать текущее содержимое затрагиваемых файлов (если уже
   существуют), выписать точные сигнатуры соседних портов/интерфейсов,
   которые понадобятся.
4. **Записать карточку.** Скопировать `docs/specs/_templates/task-card.md`
   в `docs/specs/NNN-*/tasks/<T#>-<slug>.md`, заполнить по формату:
   Цель → Контекст (инлайненный код, не ссылки — здесь обильный инлайнинг
   уместен) → Red (тест как сценарий Given/When/Then + место вставки +
   пример стиля рядом — не готовый код теста, см. «Правила») → Green
   (описание правки: что и куда встаёт — не готовый диф, см. «Правила») →
   Acceptance (точная команда запуска, напр. `go test ./modules/x/...`) →
   Boundaries (что не трогать, какие файлы не заводить сверх перечисленных).
5. **Связать с `tasks.md`.** Рядом с decomposed-пунктом дописать ссылку на
   карточку: `- [ ] T3 → tasks/T3-service.md`. `tasks.md` остаётся
   источником истины статусов — при завершении карточки `implement-task`
   сам отмечает чекбокс.
6. **Не имплементировать.** Скилл только генерирует карточки и
   останавливается — реализация не его ответственность.

## Правила

- **Карточка — не готовое решение.** Она даёт исполнителю всё, чтобы он
  сам написал тест и код: контекст (инлайн), сценарий Red, куда встаёт
  Green, критерий готовности. Вставлять в Red дословный финальный код теста
  и в Green — дословный финальный код реализации **запрещено по умолчанию**:
  если карточка — это уже готовый диф, декомпозиции не произошло, а
  локальная модель превращается в машину копирования (дороже и дольше, чем
  просто написать код самому). Дословный код — только точечное исключение,
  когда без него сценарий неоднозначен (точный текст сообщения об ошибке,
  редкий формат данных), и тогда это минимальный фрагмент, а не весь
  тест/файл.
- **«Без места для интерпретации» — про ГРАНИЦЫ задачи, не про КОД.**
  Не давать исполнителю принимать архитектурные решения (какой слой, какое
  имя, какая структура) — это описывается точно. Но сам текст кода,
  реализующий уже принятое решение, пишет исполнитель по образцу из
  Контекста, а не копирует из карточки.
- Карточка самодостаточна: исполнитель `implement-task` не должен читать
  ничего сверх неё. Если для задачи нельзя набрать достаточный контекст в
  разумном объёме — это сигнал, что задача на самом деле `requires: claude`.
- **Одинаковый паттерн правки, повторяющийся по многим файлам** (напр. один
  и тот же гейт/строка добавляется в N однотипных хендлеров) — НЕ N карточек
  с решением на каждый файл. Одна карточка: один файл разбирается полностью
  как эталон (Context/Red/Green по общим правилам выше), остальные файлы —
  списком путей с инструкцией «применить тот же паттерн самостоятельно»,
  без инлайна кода под каждый. Если паттерн неочевиден без примера на
  каждом файле — значит, файлы недостаточно однотипны для одной карточки,
  и это сигнал разбить их на 2-3 карточки по подтипам, а не на N.
- Один прогон скилла может декомпозировать сразу несколько задач `tasks.md`
  за раз — карточки от этого не перестают быть по одной на задачу (кроме
  батч-случая выше, где одна карточка сознательно покрывает несколько
  файлов одного паттерна).
